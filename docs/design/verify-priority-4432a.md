## 1. 前の形がなぜ落ちたか

- **第 1 版（予約＋使い回し）**: 予約を 1 つのファイルに置き、取り手が poll のたびに読んで譲るかを決めた。持ち主をゲート id で決めたので、持ち主の別の重いゲートが自分の予約に譲った（TV-SELF-YIELD）。持ち主に回復を禁じたので、持ち主が先頭だと誰も死んだロックを回復しなかった（TV-OWNER-HEAD-DEADLOCK）。「予約なし」を読んだ後に予約が成立しても、その取り手は `mkdir` で入れた（設定と `mkdir` の順）
- **第 2 版（予約だけ）**: 世代のファイル・持ち主の印・取得の後の身引きを足した。身引きの解放が 1 回の EIO で失敗すると生きた owner が残った（再現 A）。解放と印の間に、他の process が予約を確定失効させた（再現 C）。札の期限を 4 時間延ばしたので、止まった先頭が列を止める時間が延びた（再現 D）
- **#4432 の案 A・B と使い回し**（範囲の外）: 「同じ条件だ」を観測から推し量って合格を写した。3 回止まった
- **根（1 文）**: 誰が先に取るかを、列とロックの外にある別の状態から決めたので、観測の後の補正が要り、補正のたびに窓が出た

## 2. 形と規則

### 2.1 不変条件

| ID | 内容 | 守り方 |
|---|---|---|
| **I-mutex** | 保有者は同時に 1 人 | 排他は今の `mkdir`。変えない |
| **I-head** | 先頭として動く待ち手は同時に 1 人（前提 P60 の下） | 規則 R3 |
| **I-nostate** | 予約という状態を持たない。優先を持つのは、いま並んでいる待ち手の札だけ | ロックの外にファイルを足さない。PUT・世代・印・期限を作らない |
| **I-noundo** | 取得の後に返す道を足さない | 解放の経路は 1 行も変えない（`release` に触らない） |
| **I-deadline** | 札の期限を延ばさない・書き直さない | 急ぐ札の `deadline` も「開始＋待ちの上限」 |

| **I-gate** | ゲートの判定を変えない | 変わるのは取る順だけ。コマンド・環境・上限・集約に触らない |

### 2.2 規則

今の作り（事実）: 札は `<root>/cpu.heavy.queue/<12 桁>`。TS（`machine-lock.ts:1257-1283`）・同期 JS（`machine-lock-sync.mjs:1195-1221`）・bash（`verify-run.sh:2002-2022`）とも、自分より小さい生きた札が無い待ち手だけが回復と `mkdir` をする。番号は「列の最大＋1」。

- **R1 番号の範囲**: 定数 `BASE = 10^11`。急ぐ札は「`BASE` 未満の札の最大＋1」、ふつうの札は「`max(列の最大, BASE)＋1`」に出す。急ぐ札どうし・ふつうの札どうしは今と同じ先着順
- **R2 取り下げ**: 出した後に自分より大きい番号があれば取り下げる今の確かめを、急ぐ札では `BASE` 未満の中だけで行う
- **R3 落ち着き**: 急ぐ札の待ち手は、自分の札を出して（取り直した場合は出し直して）から `SAME_HOST_GRACE_MS`（60 秒）たつまで、回復も `mkdir` もしない。その後は今の先頭の手順のまま
- **R4 生死**: 急ぐ札を外せるのは今の規則だけ（pid の死・pid の再利用・`deadline`＋60 秒）
- **R5 引数の検査**: `priority: 'urgent'` を受けるのは名前が `cpu.heavy` のときだけ。待ちの上限が 60 秒以下なら拒む（空きでも取れないため）
- **R6 配線**: `commandmate verify --urgent`・`wait --verify --urgent`・API の `priority: "urgent"` が run に付き、gate-runner がその run の全部の `cpu.heavy` の取得に渡す。verify.yaml・exit code・migration は変えない。出せる人は他の verify の API と同じ保護で、PM だけが使うのは運用の規則。本数の上限は置かない（全員が急げば今の先着順に戻るだけ）
- GC は低い範囲の最大の `done` の札も残す。ただし旧い GC は消すので、正しさはこれに頼らない（§4 の G2）

### 2.3 受け継ぐ前提 P60

- **P60**: 1 つの process は、2 つの syscall の間で 60 秒より長く止まらない。今の設計の前提（`docs/design/merge-queue-fair-lock-4277.md` §2.4）で、札の猶予（`deadline`＋60 秒）も同じ値に乗っている
- 今の列で、先頭が他の生きた待ち手へ移るのは札が退役したときだけ。急ぐ札は公開の瞬間に前へ入るので、その瞬間に poll の途中だったふつうの先頭と重なる。R3 が無いと保有者が 2 人になる（§4 の H1。事実）
- R3 の下では、公開より前に列を読んだ poll は 60 秒の間に終わり、以後の poll は必ず急ぐ札を前に見る
- **P60 が破れたとき**: 60 秒より長く止まった先頭が動き出すと、先頭が 2 人になりうる。今の列でも、止まった先頭の札が退役した後に同じことが起きる。新しく足す弱さではない（見立て）。スリープからの復帰も同じ（壁時計。**未確認**）
- 測った値（事実）: bash の `lock_acquire` の 1 回の poll は約 83 ms（負荷 10 前後で 1 度）。`lock_wait_head` は `cpu.heavy` の経路から呼ばれない（`verify-run.sh:2308-2312`）

### 2.4 成立点と、落とす約束

- 成立点は急ぐ札の `link(2)`。それより前に列を読んだ先頭が `mkdir` に成功したら、その取り手は「急ぐ札が来た時点の保有者」で、持ち続ける。補正しない（§4 の C1）
- A2: 指定から札が出るまで（軽いゲートの間。#4433 の例で約 45 秒）と落ち着きの 60 秒の間に他が取ると、最悪で保有 1 本分（Sprint 9 の最大 56 分）待つ。空きのロックに急ぐ札が来ると、機械は最大 60 秒遊ぶ
- A3: 急ぐ札に抜かれたふつうの札は、今と同じ上限で SKIP・`held` になりうる。待ち切りの文に「急ぐ札の後ろで待った秒数」を出す
- A4: 急ぐ run の重いゲートの間（解放 → 次の札）に、ふつうの先頭が 1 本入りうる（§4 の E2）。Sprint 9 の 53 run では該当 0 本（DB の読み取り）

### 2.5 混在と切り替え

- 旧い読み手（旧い checkout の precheck・再ビルド前のサーバー・bash）は、変更なしで急ぐ札に譲る（§4 の A2・A4）。混在しても先頭は 1 人
- 旧い書き手は「最大＋1」のままなので、列に `BASE` を超える札が 1 つあれば高い範囲に入る。本番の列の最大は今 `000000000431`。再ビルド後の最初のふつうの札で切り替わる。その瞬間に待っていた旧番号の札は、急ぐ札より前のまま（一時的）
- 旧い書き手だけの列では先着順に落ちる（優先が効かないだけ。§4 の A3）
