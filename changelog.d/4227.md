- **docs(design): mem の画面と、対話・無人に応じた開始と終了の流れの設計（第 5 版）** (#4227): `docs/design/mem-ui-4227.md` に PM の決定（S-F は C の `FitTextOptions.itemCap` と provider の `BriefRequest.detail` の 2 つの欄だけを足す「全文」、既定は今どおりで C の出力と既存の試験は変えない。migration は G = v71、F = v70・E = v69、マージの順 E → F → G）と Codex の再確認 3 回（P1 3・P2 4、P1 1・P2 4、P1 1・P2 1）を反映。終了は起動／終了の排他の中で行い、**kill の対象の識別を 1 つの規則にした**：観測を `classifyAgentIdentity` に通して「同じ／違う／不明」の 3 値で返し、「同じ」のときだけ kill する。「同じ」と言えるのは、pane のプロセスの木でツールごとに宣言した名前に一致する **Agent 自身のプロセス**（shell・識別できない wrapper は採らない）を、起動の時の記録（`beginAgentSession` で同期に進める世代番号と、起動の後の pid・開始時刻）と照らして一致したときだけで、`tpgid`・`pane_pid`・shell の pid は識別に使わない（job control の無い shell では Agent が交代しても `tpgid` が同じ）。不明（読めない・値が古い・shell しか見えない・記録が空）は kill せず人の手動の停止へ案内し、観測点 × 失敗の注入の表駆動の対照と「Agent の PID は交代するが `tpgid` は同じ」の対照で固定する。送信の中の再起動が lifecycle を待たずに投げる `InstanceLifecycleBusyError` は `classifySendFailure` で `not-sent`（`lifecycle-busy`）へ写し、D1 の予約を `pending` に戻して送信の route は 409 `INSTANCE_LIFECYCLE_BUSY` を返す（試験は実際の `sendUserMessage` 経由で配送の記録・境界・打鍵 0 まで）。kill の全経路は tmux の `killSession` から逆引きしてガードで固定し（`session-cleanup.ts` の worktree の削除も排他へ通す・グローバルの session は理由つきで除外）、排他の順序と再入（外からは lifecycle → input、送信の中の再起動は待たずに失敗、同じ所有者は合流、失効した ticket には渡さない）を定めた。一度立った強制終了（`end_forced`）は同じ依頼では消さず、依頼の所属（repository・branch）を確定の `pin` に含めて最終の target と照合する。開くときの選択は送信の直前の排他の区間でも見せた境界と照合し、`decline`・`full` の失敗は本文を打たずに 409 `boundary_changed` を返して下書きを残す。人への質問は C の JSON の実際の形で分類し、試験の表を入口ごとの適用条件と例外の表にした。
