# 実機切り分け手順書: Android Chrome の「不正な疑いのある通知」（Issue #2126）

> Epic #2002 の実機 UAT（`2002-push-uat-record.md` §3）で踏んだ事象の**再現条件を確定する**ための手順。
> 本書は手順書であり記録ではない。結果は `2002-push-uat-record.md` に節を足して書く。

## 0. この手順書が答える問い

**「Chrome の suspicious 判定は、通常運用の頻度でも起きるのか。」**

#2126 の受入条件の筆頭がこれである。常時起きるなら Epic #2002 が Android で丸ごと無効になり
最優先の欠陥、UAT の高頻度が誘因なら実害は小さく手順書に注意を書けば済む。**両者で対応が変わる。**

## 1. 先に押さえるべき制約（設計上の難所）

### 1.1 サーバ側からは観測できない

suspicious 判定された通知も、**サーバから見れば送信成功**である。
`push-sender` は失敗（403 / 404 / 410）しかログせず、成功は無言。

**#2124 で入れた `delivery-health` はこの事象を検知しない。** あれは 403 / 410 を
「この端末に届いていない」と記録するもので、**suspicious 判定は 2xx で返る**ため記録されない。
（#2126 本文の対策案 2 は 403/410 の可視化として正しいが、**本事象の検知手段にはならない**。）

したがって **判定は端末の目視が唯一の手段**であり、1 回の試行につき人間が 1 回見る必要がある。

### 1.2 フラグの解除方法が未確定 → 試行回数に上限がある

一度フラグが立った後、何をすれば元に戻るかを**まだ確かめていない**。
解除できなければ実質 1 回しか撃てないので、**Phase 1 で解除方法を先に確定する**。

### 1.3 端末が 1 台しかない

Android は 1 台。「フラグが立った端末」と「立っていない端末」を同時に比べられないので、
**時系列の前後比較**に頼る。したがって**他の変数を動かさない**ことが重要になる。

## 2. UAT 時に実際に何を送ったか（実測 2026-08-27）

`logs/server.log` から抽出した送信イベント。**成功した待機通知は無言なので含まれない**
（少なくとも陽性対照で 2 回、L-2③ で 1 回が端末に届いている）。

| 時刻 (UTC) | 種別 |
|---|---|
| 14:20:18 / 14:20:44 | 購読登録（Android / iPad） |
| 14:23:42 | 送信失敗 403（iPad・#2124 の欠陥） |
| 14:28:02 | 消し込み |
| 14:30:38 | 消し込み |
| 14:32:39 | 消し込み |
| 14:39:16 | 消し込み |
| 15:05:23 | 消し込み |
| 15:06:50 / 15:07:51 | 再購読（SW 入れ直し） |
| 15:16:12 | 失敗通知 |
| 15:18:51 | 失敗通知（＋ Android 購読が 410 で削除） |
| 15:20:19 | 再購読 |
| **15:22:24** | 失敗通知 ← **この直後に「不正な疑いのある通知」を観測** |

ログに出た送信は **8 件 / 62 分**。無言の待機通知を足しても **11〜12 件 / 62 分 ≒ 11 件/時**。

**これは「異常な高頻度」と言い切れる量ではない。** 並列オーケストレーションで
ワーカーが数本走れば同程度になりうる。**「UAT の高頻度が誘因」という仮説は弱い**ことを
先に認識しておくこと（ただし否定もされていない。だからこの手順書がある）。

なお **購読の入れ直しを 3 回**している。短時間の再購読が判定材料になっている可能性は
排除できていない。Phase 3 の変数候補に入れる。

## 3. 準備

- サーバは develop（#2123 / #2124 マージ後）でリビルド済みであること。
  確認: `curl -s http://127.0.0.1:3000/api/push/vapid` → `{"configured":true,...}`
- **起動時 VAPID セルフチェックが無言であること**（＝設定が正常）。
  `grep -aic vapid logs/server.log` が 0 なら正常。何か出ていたら先にそれを直す
- ログを流す:
  ```bash
  tail -n 0 -F logs/server.log | grep -aE '\[push/|push-subscriptions'
  ```
- 使い捨て worktree を 1 つ使う（本番の作業に割り込まないため）

## 4. Phase 1 — 解除方法の確定（**最初にやる**）

いまフラグが立っている状態から始める。立っていなければ Phase 2 へ。

1. Android の通知シェードで「不正な疑いのある通知」のカードを開く
2. **そこに出る選択肢をそのまま記録する**（「表示」「ブロック」「配信を継続」等、
   文言は Chrome の版で変わる）
3. 「表示する」に相当する操作を選ぶ
4. 通知を 1 通送り、**次の通知が普通に出るか**を見る

**記録すること**:
- [ ] カードに出た選択肢の**文言そのまま**
- [ ] 選んだ操作
- [ ] その後 1 通目が普通に出たか / まだ伏せられるか
- [ ] `⋮ → 設定 → サイトの設定 → 通知 → myweb-3000.kewton.org` の状態

**解除できなかった場合**は、サイトの通知を解除 → 再購読で戻るかを試す。
それでも戻らないなら **試行は 1 回しかできない**ので、Phase 2 を最も価値の高い 1 回に絞る。

## 4-B. Phase 1 の結果（2026-08-28 実施・確定）

**解除方法は「常に許可」。** カードは 2 段構成で、1 段目で `[登録解除] [通知を表示]`、
「通知を表示」を押すと**その 1 通が読めるようになり** 2 段目の `[登録解除] [常に許可]` が出る。
「常に許可」で `myweb-3000.kewton.org からの通知を許可しました` が表示され、
**直後に送った 1 通は普通に表示された**。

| 試したこと | 結果 |
|---|---|
| 時間経過（1 時間以上） | 解除されない |
| カードを 1 枚消す | 解除されない |
| 全通知を消す | 解除されない |
| 「通知を表示」 | その 1 通だけ読める（一時的） |
| **「常に許可」** | **恒久解除** |

カードの文面（原文）:

```
不正な疑いのある通知
myweb-3000.kewton.org から不正な疑いのある通知が送信されました。
```

### 付随して確定した事実

- **判定は Android Chrome のもの。** 同じ通知が iPad では終始正常に表示され、
  サーバは一貫して `delivered: 2 / failed: 0` だった。
  **Chrome は通知を受け取ったうえで中身を伏せ、警告に差し替えている**
- **「登録解除」が両方の画面で左側にある。** 誤って押すと購読が消え、
  CommandMate 側からは次の送信時の 410 Gone（`push-subscription-removed`）としてしか分からない
- **「常に許可」を選んだ場合はサーバ側に一切痕跡が残らない。**
  伏せられていたことも解除されたことも観測できない

### Phase 2 への含意（手順書の想定外だった点）

**「常に許可」の後は二度と判定されない可能性がある。**
その場合 Phase 2 は「起きなかった」ではなく **「測定不能」** になる。
結果を「通常頻度では起きない」と書いてはいけない。

「常に許可」を取り消して元の条件に戻せるかは**未確認**であり、
戻せなければ以後どの試行もできなくなる。**取り消しを試す前に、
それが唯一の観測手段を失う賭けであることを認識すること。**

## 5. Phase 2 — 通常運用の頻度で起きるか（本命）

**フラグが解除された状態から始める。**

「通常運用」を **1 時間あたり 3〜4 件、間隔 15〜20 分**と定義する
（並列ワーカー 2〜3 本が待機・完了する程度の想定）。

1. 待機通知を 1 通送る（Auto-Yes 無しで承認プロンプトを出す）
2. **15 分あける**
3. 失敗通知を 1 通送る（`commandmate verify --gates lint` を落とす）
4. **15 分あける**
5. 待機通知をもう 1 通
6. **15 分あける**
7. 失敗通知をもう 1 通

**期待（仮説どおりなら）**: 4 通とも普通に表示され、suspicious 判定は出ない。

**記録すること**:
- [ ] 4 通それぞれが普通に出たか、伏せられたか
- [ ] 伏せられた場合、**何通目で**そうなったか
- [ ] 各通知のサーバ側ログ行（時刻と種別）

**ここで再現したら Phase 3 は不要。** 「通常頻度でも起きる」が確定し、
#2126 は最優先の欠陥になる。

## 6. Phase 3 — 高頻度で再現するか（Phase 2 が緑のときだけ）

Phase 2 で起きなかった場合に、**誘因を特定する**。1 回に 1 変数だけ動かす。

| # | 変数 | やり方 | 判定 |
|---|---|---|---|
| 3-1 | **頻度** | 5 分間に 6 通（UAT と同程度の密度） | 出れば頻度が誘因 |
| 3-2 | **再購読** | 短時間に解除→再購読を 3 回してから 1 通 | 出れば購読の作り直しが誘因 |
| 3-3 | **未操作** | 通知を一度もタップせずに 6 通 | 出れば「無視され続けた」が誘因 |

**3-3 が有力な候補である**: Chrome の判定は利用者の操作履歴を見る設計が知られており、
UAT では**ほぼすべての通知をタップせずに放置した**（ログ判定で済ませたため）。
実運用では対応のためにタップするので、ここが違えば実害は小さい。

**変数を 2 つ同時に動かさないこと。** 試行回数に上限がある以上、
1 回で 2 つ動かすと何が効いたか分からなくなる。

## 8. この手順書が扱わないこと

- **iOS 側**: APNs にこの機能は無く、UAT でも iPad は正常に表示された。対象外
- **Chrome の判定ロジックの解明**: 外部サービスの内部であり、こちらから観測できない。
  **入力（頻度・操作履歴・購読の作り直し）を動かして出力を見る**ことしかできない
- **恒久対策**: 誘因が確定してから別途決める。本書は切り分けまで
