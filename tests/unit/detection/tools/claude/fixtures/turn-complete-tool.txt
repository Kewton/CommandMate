[38;5;231m[49m⏺[39m [1mHow Terminal Multiplexers Survive Disconnects[0m

  When you SSH into a machine and run a long job, the job dies the moment your connection drops. Terminal multiplexers like tmux and GNU Screen exist to break that coupling, and understanding how
  requires knowing what actually kills the process.

  [1mThe problem: SIGHUP and the controlling terminal[0m

  Every interactive process is attached to a [3mcontrolling terminal[0m — historically a physical teletype, today a pseudo-terminal (PTY) pair. A PTY has two ends: the master, held by whatever is drawing
  your screen (sshd, your terminal emulator), and the slave, which the shell and its children open as stdin/stdout/stderr.

  The kernel tracks which session each process belongs to and which terminal that session controls. When the master end of the PTY closes — your SSH connection drops, you close the window — the kernel
  notices the terminal has been hung up. It delivers [38;5;153mSIGHUP[39m to the foreground process group, and the session leader propagates it to its children. The default disposition of SIGHUP is termination.
  Your job dies not because the network failed, but because the kernel deliberately told it to.

  [1mThe solution: put a server in between[0m

  A multiplexer splits the arrangement into two processes. When you first run [38;5;153mtmux[39m, it forks a long-lived [1mserver[0m daemon that detaches from your terminal entirely — it calls [38;5;153msetsid()[39m to become its own
  session leader with no controlling terminal, so there is no terminal that can ever hang up on it.

  That server then allocates its [3mown[0m PTYs, one per window or pane, and spawns your shells against those. Your shell's controlling terminal is a PTY owned by the server, living entirely inside the
  machine. It has no relationship to your SSH connection.

  What you interact with is a thin [1mclient[0m process. It connects to the server over a Unix domain socket (typically under [38;5;153m/tmp/tmux-$UID/[39m), forwards your keystrokes in, and renders the screen updates
  the server sends back. When your connection drops, only the client dies. The server never notices anything beyond a closed socket; it keeps reading output from the still-running shells and updating
  its in-memory screen model.

  [1mReattaching[0m

  Running [38;5;153mtmux attach[39m starts a new client, which connects to the same socket. The server replays its saved screen state — cursor position, scrollback, pane layout — and you're back exactly where you
  left off.

  This is also why [38;5;153mnohup[39m and [38;5;153mdisown[39m are weaker alternatives: they suppress SIGHUP but discard the terminal, so you lose interactivity and output. A multiplexer preserves both.

[38;5;231m[49m⏺[39m [1mWhy File Descriptors Survive a Detached Session[0m

  The short answer is that a file descriptor is a property of a [3mprocess[0m, not of a session, a terminal, or a network connection. Detaching doesn't touch the process, so it doesn't touch the
  descriptors.

  [1mThree layers, not one[0m

  It helps to see the kernel's actual structure. There are three distinct levels of indirection:

  1. [1mThe per-process descriptor table.[0m An fd is just a small integer indexing into an array the kernel keeps for each process. Fd [38;5;153m1[39m in your shell and fd [38;5;153m1[39m in mine are unrelated entries in unrelated
     tables.
  2. [1mThe open file description.[0m Each table entry points to a kernel object holding the file offset, the access mode ([38;5;153mO_RDONLY[39m, [38;5;153mO_APPEND[39m), and status flags. This object is reference-counted and shared
     — [38;5;153mdup()[39m, [38;5;153mdup2()[39m, and [38;5;153mfork()[39m all create new pointers to the [3msame[0m description rather than a copy.
  3. [1mThe underlying object[0m — an inode, a pipe buffer, a socket, a PTY slave.

  Nothing in this chain records "which SSH connection was responsible for creating this." There's no back-reference for a disconnect to follow.

  [1mWhat a detach actually closes[0m

  When a tmux client exits, the kernel walks [3mits[0m descriptor table and decrements refcounts. The client's socket to the server closes, and its end of the terminal closes. That's the extent of it.

  Your shell is a different process, in a different session, with a different descriptor table. Its stdin, stdout, and stderr point at a PTY slave that the tmux [3mserver[0m opened, and the server still
  holds the master end open. Because the master's refcount never drops to zero, the kernel never signals a hangup on the slave, and the shell's fds remain perfectly valid — readable, writable, and
  pointing at exactly the same offsets.

  [1mInheritance is a snapshot, not a link[0m

  This is the crucial asymmetry. When the server forked your shell, the child received copies of the descriptor table entries. From that instant the two are independent: the child can close, reopen,
  or [38;5;153mdup2()[39m freely without affecting the parent, and the parent's death won't invalidate the child's fds. Inheritance happens once, at [38;5;153mfork()[39m. It does not create an ongoing dependency that a later
  disconnect could sever.

  The same principle explains why an unlinked file stays readable — [38;5;153mrm[39m removes the directory entry, but the inode survives as long as some descriptor references it. Descriptors keep objects alive;
  they don't depend on names, terminals, or parents.

  [1mWhy hangups are signals, not fd revocation[0m

  Even the SIGHUP case isn't the kernel invalidating descriptors. When a terminal is hung up, the kernel sends a [3msignal[0m. If the process ignores it or handles it, the fds are still there — reads on the
  dead PTY return [38;5;153mEIO[39m or zero bytes, but the descriptor itself remains a valid table entry until explicitly closed. Unix has no mechanism for one process to yank another's descriptors away.

  [1mReattaching[0m

  A new client connects to the socket and receives fresh descriptors of its own. The server's PTY masters, and your shell's slaves, were never disturbed. The plumbing at the far end is entirely
  unchanged — only the last hop was rebuilt.
