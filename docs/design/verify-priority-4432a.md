### 2.2 規則

今の作り（事実）: 札は `<root>/cpu.heavy.queue/<12 桁>`。3 実装とも、自分より小さい生きた札が無い待ち手（先頭）だけが回復と `mkdir` をする（TS は `machine-lock.ts:1257-1283`）。番号は「最大＋1」。

- **R1 番号の範囲**: `BASE = 10^11`。急ぐ札は「`BASE` 未満の札の最大＋1」、ふつうの札は「`max(列の最大, BASE)＋1`」に出す。範囲の中は今と同じ先着順
- **R2 取り下げ**: 出した後に自分より大きい番号があれば取り下げる今の確かめを、急ぐ札では `BASE` 未満の中だけで行う。安全ではなく、急ぐ札どうしの先着順のための規則
- **R3 落ち着き**: 急ぐ札の待ち手は、自分の札を出して（取り直したら出し直して）から、**自分が終えた sleep の合計が `URGENT_SETTLE_MS`（660,000 ms）に届くまで**、回復も `mkdir` もしない。届いた後は今の先頭の手順のまま。定数は札の猶予（`SAME_HOST_GRACE_MS`）と別に持つ。時計は読まない（時計の段差・スリープで早まらない。§4 の X3）。**数えるのは、内部の本物の sleep に頼んだ長さの合計**（TS の `sleep`、同期 JS の既定の `sleepSync`。claude-5 の Y7: 早く返らない）。`setTimeout` の切り捨て（1 回 1 ms 未満。11 分で約 2.6 秒）は余裕の 1 分の内
- **R4 生死**: 急ぐ札を外せるのは今の規則だけ（pid の死・pid の再利用・`deadline`＋60 秒）
- **R5 引数の検査**: `priority: 'urgent'` を受けるのは名前が `cpu.heavy` のときだけ（他の名前は呼び手が無いので例外）。次のどれかに当たる取得は、**ふつうの札に戻して警告を出す**（判定を変えない）: 待ちの上限が落ち着きの 3 倍（33 分）に満たない／呼び手が `sleep` を差し替えた／poll の間隔が 0 以下。3 倍の根拠: 落ち着きの実時間は sleep の合計の 1.02〜1.25 倍（Y7）で、取り直し 1 回（§2.5）まで見込むと 2 回分で 22 分強。もう 1 回分を余裕に持つ。本番の上限は 5,400 秒。結果に効いた優先（`urgent`／`normal`）を返す
- **R6 配線**（PR-2）: `commandmate verify --urgent`・`wait --verify --urgent`・API の `priority: "urgent"` が run に付き、gate-runner がその run の全部の `cpu.heavy` の取得に渡す。verify.yaml・exit code・migration は変えない。PM だけが使うのは運用の規則。本数の上限なし。**効いた優先を API の応答・ゲートの `log_tail`・run-log に残す**（再ビルド前のサーバーは欄を黙って捨てる。応答に無ければ CLI が警告する）
- GC は変えない（試作の「低い範囲の最大も残す」は外す。正しさに使わず、bash が消す）

### 2.3 前提 P-poll と、今の前提との関係

- **P-poll**: どの待ち手の 1 回の poll も、列を読んでから最後の書き換えまでが、急ぐ待ち手の落ち着き（11 分）より短い
- **#4288 の P0 との関係**（`docs/design/machine-lock-owner-atomic-4288.md:15-18`。PM 決定）: P0 は「手順の途中で、どの書き手も読み手も 10 分を超えて止まらない」。停止 1 回の長さの前提で、poll の全体の長さは言っていない（事実）。P-poll は「P0 の停止 1 回＋実働 1 分」なら成り立つ。**P0 の内なのに P-poll から外れるもの**は 2 つ: 1 回の poll の中で停止が重なって 11 分を超える／実働だけで 1 分を超える（測った bash の poll は約 83 ms。負荷 10 前後・回復なしで 1 度）
- **今の作りが「先頭は 1 人」を何で守っているか**（事実）: 札の猶予。生きた先頭の札は「残りの待ち＋60 秒」止まると外れ、次の待ち手が先頭になる。#4288 の「60 秒〜10 分の停止の後の再開は `link` の排他と inode の確かめで安全」は、公開の途中の**書き手**には効くが、**古い判定で退かす回復者**には効かない（I8 (a) の文は書き手を名指している。見立て）。develop のまま（優先なし）で再現した（事実。順は hook で固定）: 先頭 N が死んだ保有者を判定した後に 65 秒止まる（待ちの上限は 0.3 秒）→ H2 が N の札を外して回復して取る → N の rename が H2 の生きたロックを退かす → その窓に H3 が `mkdir` → H2 と H3 が同時に保有（§4 の D1。claude-5 も 69 秒の停止で再現）。2 秒の停止では起きない。本番の上限（5,400 秒）で、P0 の内の停止（10 分以下）でこれが起きるのは、先頭が自分の期限の 9 分以内で止まったときだけ
- **R3 が足すもの**: 急ぐ札は公開の瞬間に前へ入るので、落ち着きが無いと上と同じ順が停止なしで起きる（§4 の H1）。落ち着き 11 分の下では、N が 11 分より長く止まらない限り起きない。P0 の停止 1 回（10 分）は内に入る。**P0 の内では窓を広げない**（上の 2 つを除く）。**P0 の外では今より狭い所がある**: 今は「残りの待ち＋60 秒」まで害の無い停止が、急ぐ札が来ると 11 分で L1 になる（残りの待ちが 10 分を超える先頭。例: 残り 60 分の先頭が 15 分止まる。今は害なし）
- **P-poll が破れたとき**: 落ち着きより長く止まっていた待ち手が動き出すと、急ぐ札の保有者のロックを退かしうる。第三者の `mkdir` が重なると保有者が 2 人になる（§4 の L1。limit の行として固定し、直さない）
- スリープ: 全部の process が一緒に止まる。落ち着きは sleep の合計なので、スリープの長さは数えない（見立て。試験はしていない）。Node の単調な時計がスリープ中に進むかは測れなかった（**未確認**。この機械にスリープの履歴が無い）。設計は時計に頼らない

### 2.4 成立点・費用・落とす約束

- 成立点は急ぐ札の `link(2)`。それより前に列を読んだ先頭が `mkdir` に成功したら、その取り手は「急ぐ札が来た時点の保有者」で、持ち続ける（§4 の C1）
- **費用（A8 の a）**: 急ぐ札は、出してから 11 分（sleep の合計。実時間はそれ以上で、poll 250 ms で約 1.02 倍）は取らない。保有者の残りが 11 分より長ければ損は 0、短ければ差の分だけ機械が遊ぶ（最大 11 分。空きのロック・前の急ぐ札の直後も同じ）。**重いゲート 1 本ごと**に払い、2 本目以降は前のゲートの解放の直後に札を出すので、ほぼ毎回 11 分遊ぶ。契約の run は `unit-related` の 1 本（Sprint 9 の 53 run で 2 本以上は 0）。`--gates` なしの run（`integration`・`unit`）と precheck（2 段）は 2 本
- **それでも入れる価値**（見立て）: Sprint 9 の #4433 は、最初の判定まで 3.5 時間・ロックの待ちの合計 5.98 時間。優先があれば各回の待ちは「保有者の残り（最大 56 分）＋最大 11 分」。最初の判定は、当時の保有者の残りが 16 分だったので損なしで約 2 時間 26 分早い。列が空のときの `--urgent` は損なので、team.md §10-4 に「列に待ちがあるときだけ」と書く
- A2: 指定から札が出るまで（軽いゲートの間。約 45 秒）に他が取ると、最悪で保有 1 本分待つ
- A3: 抜かれたふつうの札は今と同じ上限で SKIP・`held` になりうる。待ち切りの文に、急ぐ札の後ろで待った秒数を出す
- A4: 重いゲートの間（解放 → 次の札の数 ms）に、ふつうの先頭が 1 本入りうる（§4 の E2）
- `onWait`（PR-2）: 落ち着きの間は空きでも呼ばれ、run の枠が返る（今は空きなら呼ばれない。`gate-runner.ts:1035-1041`）。注と #3884 H-11 の試験の期待を直す

### 2.5 混在・切り替え・番号の再利用

- 旧い読み手（旧い checkout の precheck・再ビルド前のサーバー・bash）は、変更なしで急ぐ札に譲る
- 旧い書き手は「最大＋1」のまま。列に `BASE` を超える札が 1 つあれば高い範囲に入る。**切り替えは PR-1 のマージと再ビルドで起きる**（PR-2 を待たない）。その瞬間に待っていた旧番号の札（今の最大は `000000000431`）は急ぐ札より前のまま。旧い書き手だけの列では先着順に落ちる
- **低い範囲の番号は恒久に再利用されうる**（事実）: どの GC も「全体の最大より小さい `done`」を消す。bash は変えないので、ずっと続く
- TS・同期 JS は判定のときの token で外すので、別の札に当たるのは `markDone` の読み直しと rename の間だけ。**bash は token を読み直して外す**（`verify-run.sh:2008-2009`）ので、判定の読み（`:1358`）から mv までに番号が入れ替わると、新しい生きた急ぐ札を外す（claude-5 の X5。事実）
- GC も名前で消す（`done` を読んでから `rm` まで。3 実装とも）。その間に他の GC が同じ番号を消し、新しい急ぐ札が出ると、生きた札を消す。GC の規則を足さないので、低い範囲は取得のたびに空になり、急ぐ札はほぼ毎回番号を使い直す（当たる機会は増える）
- 外された（消された）急ぐ札は、その窓の中で出されたばかり。窓が 11 分より短い限り落ち着きの中にいて、先頭として動いていない。どの窓（`markDone`・bash の読み直し・GC）も 1 回の poll の一部。持ち主は `ticket-lost` で取り直し、落ち着きを数え直す（§4 の G2・G3）。**害**: その札が最大 11 分遅れ、急ぐ札どうしの先着順を失う。窓が 11 分を超えるのは P-poll の外
