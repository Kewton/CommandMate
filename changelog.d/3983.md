- **fix(cli): `wait` / `ask` / `verify` の `--timeout` をコマンド全体の期限として全取得に伝え、期限切れを途中の catch で握りつぶさない** (#3983): `--timeout` はポールの中の取得（#3974）にしか効かず、ポールの前の取得（`wait --verify` / `--require-work` の task 一覧、`--instance` の解決と capabilities の `rawGet`）には期限が無かったため、サーバーが応答しないと undici の既定（約 300 秒）まで止まり、その後も劣化動作の catch（`resolveWaitedTaskId` の Note・`resolveWaitInstance` の「元の宛先で続ける」・`fetchRecentMessages` の `null`・capabilities の包み直し）が期限切れを通常の失敗に変えて待機や検証へ進んでいた。CLI の `ApiClient` に `withDeadline(deadlineAt)` を追加し、派生 client の `get` / `post` / `patch` / `rawGet` は本文の読み（`json()` / `text()`、`rawGet` は呼び出し側の読みも）を終えるまでを 1 回の取得として期限で打ち切り、`DeadlineExceededError`（exit 124、`ApiError` に包まれても `transportError` / `cause` で識別）を投げる。劣化動作の catch は期限切れだけ再送出する。`wait` / `ask` は action の冒頭を `--timeout` の起点にし（ポールの期限もそこから数える。turn の採用窓はポールの開始のまま）、`verify --timeout` は開始の POST と run の取得にも期限を入れ、ポールの待機を期限で切り詰めて最後の 1 回を期限の時刻に読む（期限の 2 秒前より後に始まる読みは期限の 2 秒後まで待つ。期限の直前に終わった run も判定を返す）。`ask --async` の relay の両端の解決も期限に含め、`whoami` の worktree 一覧の読みも期限切れを再送出する。**範囲外**: `wait --verify` の完了後の検証は期限の無い client のまま中断しない。`ask` の送信 POST（`--async` の relay 登録の POST も）は中断せず、返った時点で期限を過ぎていれば「送信は済んでいる」と書いて exit 124（ポールしない）。`ask` の完了後の返答の読み（台帳・重なりの台帳・画面）は `--timeout` で 124 にせず、各取得を返答の猶予（15 秒）で打ち切って既存のフォールバックへ進む。`--timeout` を付けない `wait` / `verify` の振る舞いは変わらない。 再発防止として、`--timeout` 付きの `wait` / `ask` / `verify` の全取得が期限の signal を持つことと、3 コマンドから届く CLI モジュールの catch が期限切れを握りつぶさないこと（理由つきの許可リスト）をガードテストで固定した。
