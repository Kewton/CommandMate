# 実シェル予算が守る「同時フル `test:unit` の本数」の実機記録（Issue #1985）

#1950 が入れた `REAL_SHELL_SUBPROCESS_TIMEOUT_MS` は「負荷下の p99.9 = 16.5s に対して約 1.8 倍」
という根拠を持っていた。**その負荷が何だったのかがどこにも書かれていなかった**、というのが本 Issue である。
実際には「同時フル実行 1 本＋意図的なプロセス生成圧」だった。#1977 が 2 本同時で回したとき
ガードは 44 回作動し、それは**設計どおりの作動**だったのに、誰も「2 本まで守る」とは言っていなかった
ため欠陥として読まれた。

本書は「数字を上げた」ことの記録ではなく、**その数字が守る条件を宣言し、その条件で測り直した実測**である。
[docs/qa/1917-parallel-unit-mutex.md](./1917-parallel-unit-mutex.md) と同じ立場で、
成果物の中心はコードではなく §3 の表である。

## 2. 「規約か機構か」（本文の検討事項 1、先に決めた）

**規約を選んだ。** ただし「機構が面倒だから」ではない。機構の側に具体的な欠陥がある。

vitest でランに 1 回だけ走るフックは `globalSetup` である。そこでマシンロックを取らせると、
**すでに `cpu.heavy` を保有した状態でこのコマンドを起動している `unit` ゲート自身が、自分を待つ**。
ロックの規約（[docs/design/verification-config.md](../design/verification-config.md) 9.2）に
再入の概念は無いので、機構版は設定 1 行ではなく**再入プロトコルの新設**であり、その失敗は
「ワーカーが完了したか」を裁定するゲートの中でのデッドロックになる。
待ち切れた場合も FAIL ではなく `SKIP reason=mutex-wait` ＝ **exit 99（裁定不能）**（9.4）である。

規約の代償は「破られうる」こと、機構の代償は「破られたことが見えなくなる」こと。
前者を選び、**破られた 1 回分をガードの余裕で吸収する**（§4）。

本文の検討事項 3（同時実行を検出してガードを緩める / skip する）は採らない。
裁定が「そのとき他に何が走っていたか」の関数になり、これは #1917 が失格条件として名指した性質
（負荷で反転する exit code は裁定ではない）そのものである。

## 3. 実測

### 3.1 条件

- 28 コア / node 24.1.0 / vitest 4.1.2 / 2026-08-24 09:31-09:47
- 観測側 ＝ `fix/1985-real-shell-budget-concurrency` の worktree。
  負荷生成側 ＝ `$HOME/cm1985-lg{1,2,3}`（`git archive HEAD` で撒いた独立 checkout。
  `node_modules` は APFS clone）。N 本を同時に起動する。
- **測定時だけガードを 240s / 予算を 600s に引き上げた。** 呼び出しを殺すガードは、
  そのガードを決めるために必要な裾を切り落としてしまうため。
- 各条件の直前に `ps -eo pid,command | grep vitest` で他ワーカーの vitest が 0 件であることを確認。
- マシンは並列オーケストレーションの通常負荷を抱えたまま（最初の run 開始前で load avg 35.91）。
  **N は「フルスイートの本数」であって、マシン上の全負荷ではない。**
- 母集団はファミリから**自前の `it()` timeout を宣言しているテストを除いた**もの。
  それらは本件の定数を継承しないため。除外されるのは `verify-run.test.ts` の 1 テストで、
  4 条件で 60s / 108s / 152s / 196s かかっている。
  どの N でも最遅テストは `REAL_SHELL_SUBPROCESS_TIMEOUT_MS` を実呼び出しに渡すファイルの中にあった。

再現手順:

```bash
NODE_ENV=test npx vitest run tests/unit --reporter=json --outputFile.json=/tmp/run.json
node scripts/measure-real-shell-budget.mjs --guard=60000 /tmp/run.json
```

### 3.4 N=4 の赤は何だったか（ガードでは直らない）

4 本すべてが赤になったが、**ガード超過は 1 件も無い**（測定用に 240s へ上げてあるため当然だが、
仮に 30s でも該当は 4 標本 ＝ 全部 `verify-run.test.ts`）。実際の内訳:

| 落ちたもの | 形 | ガードで直るか |
|---|---|---|
| `skills/cmate-verify/verify-run.test.ts`（4/4 run） | 195.5s で**自前の 180000ms 予算**を超過 / 内側の bash スイートが赤 | 直らない（自前予算） |
| `lib/file-tree.test.ts`（2 run） | `ENOENT ... /T/file-tree-test-<epoch>` ＝ 砂箱の競合 | 直らない |
| `tmux-history-limit.live.test.ts` | 実 tmux の共有資源衝突 | 直らない |
| `components/GitPane.test.tsx` | React の描画待ちレース | 直らない |
| `cli/commands/status-issue.test.ts`（2 run） | `STACK_TRACE_ERROR` | 直らない |

**N=4 はガードのサイズで守れる領域ではない。** これが「N=4 まで守る」と宣言しなかった理由である。

## 4. 採った値

```
REAL_SHELL_CONCURRENT_FULL_RUNS = 2       宣言（1 台で同時に走ってよいフルスイートの本数）
REAL_SHELL_SIZING_CONCURRENCY = 3         サイズ決定条件（宣言 + 超過 1 本）
REAL_SHELL_GUARD_MARGIN_MIN = 1.8         #1950 から引き継いだ margin の下限
REAL_SHELL_SUBPROCESS_TIMEOUT_MS = 60000  1.8 x 25873ms (N=3 の最遅) = 46571ms を満たす最小の丸い値
REAL_SHELL_TEST_TIMEOUT_MS = 180000       ガードの 3 倍（#1950 の関係をそのまま保った）

   50000 の余裕                            = 7.4%
   同一条件の run 間ばらつき（§3.2）        = 12.4%
   60000 の余裕                            = 28.9%
```

50s は規則を紙の上では満たすが、**その規則を作った実測自身のばらつきに負ける**。
よって **`REAL_SHELL_SUBPROCESS_TIMEOUT_MS = 60000`** — 規則の下限を、実測が示したばらつきより
大きく超える最小の丸い値。

| N | 30000 の比 | **60000 の比** |
|---|---|---|
| 2（宣言） | 2.52 | **5.04** |
| 3（サイズ決定） | 1.16 | **2.32** |
| 4 | 1.00 | **2.00** |

宣言 N=2 における **p99.9 (9854ms) との比は 6.09 倍**。

`REAL_SHELL_TEST_TIMEOUT_MS` は #1950 の 3 倍関係を保ったまま **90000 → 180000** へ動かした。
比率を選び直さなかったのは、1 つの理由で 1 つの数字だけを動かすためである。
**代償**: 本当にハングした呼び出しの報告が 30 秒遅くなる。ガードを持たない 57 ファイルでは 3 分になる。
ハングは無限なので、到達可能などのガード値でも「捕まえられない」ことは起こらない。
変わるのは報告までの実時間だけである。

## 6. 運用規約

**1 台で同時に走らせてよいフル `npm run test:unit` は 2 本まで。**
`mutex: cpu.heavy` により verify 由来は常に高々 1 本なので、これは
「手で回してよいのは 1 本」と同義である。3 本目を回した run の赤は、
diff についての裁定として使ってはならない（§3.4 のとおり、ガードで守れない形で落ちる）。

宣言を変えるときは `scripts/measure-real-shell-budget.mjs` でスイープを取り直し、
`tests/helpers/real-shell-budget.ts` の `REAL_SHELL_LOAD_SWEEP` と本書を同時に更新すること。
`tests/unit/guards/real-shell-test-budget.test.ts` が両者の一致とサイズ決定規則を固定している。
