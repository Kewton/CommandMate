### 3.4 気づき（次の Issue の種）

**A. 待機エッジの観測は機会的で、短い待機は観測すらされない（手順書が想定していない条件）**

alias への L-2 は 3 回目でようやくゲートのログが出た。

| 回 | 検出 → Auto-Yes 応答 | `prompt-push-suppressed` |
|---|---|---|
| 1 回目 | 244 ms | 出ない |
| 2 回目 | 231 ms | 出ない |
| 3 回目 | 1,665 ms | **出た** |

`observeWaitingEdge` の呼び出し元はポーラーのティックか worktree 一覧 API のプローブだけで、
Auto-Yes が 230 ms で答えるとその隙間を誰も見ていない。**利用者から見た結果（鳴らない）は同じだが、
機構は「抑止された」ではなく「観測されなかった」**である。3 回目は `/api/worktrees` を
タイトなループで叩いて窓に入れた。手順書に「短い待機では抑止ログが出ないことがある」旨の
注記が要る。

**B. 成功した送信はログに出ない — ログの沈黙を「送っていない」と読んではいけない**

`waiting-push-notifier` は `waiting-push-failed` のみ、`push-sender` は `push-send-failed` /
`push-subscription-removed` のみをログする。**成功は無言**。実施中に一度この推論を誤り、
「送信ログ 0 行だから鳴っていない可能性」と判断しかけた。**判定は端末の目視が唯一の手段**である。
手順書 §1.3 の期待ログ例は `resolution-push-sent`（成功をログする側）だけなので、
待機通知側も同じだと読める。注記が要る。

**C. リクエストログが無いため「届いていない」を切り分けられない**

購読が成立しない間、`/api/push/subscriptions` への POST が到達したかを確かめようとしたが、
**このサーバはリクエストをログしない**（陽性対照として自分で `/api/push/vapid` を叩いても 0 行）。
`push-subscription-registered` / `post-failed` の 2 行しか手がかりが無く、
**400（不正ペイロード）は無言**なので「呼ばれていない」と「弾かれた」が区別できない。

**D. 端末側の前提がドキュメントに無い（#2123）**

実施に必要だったのに、どこにも書かれていなかったもの: HTTPS が要ること／iOS はホーム画面 PWA が
必須で Android は不要なこと／**アプリ内の More 画面のボタンを押すまで OS の通知一覧にサイトが
現れないこと**（今回、OS 設定を先に見て「許可済みのはず」と誤認した）。

**E. Cloudflare Access のセッションと通知タップの着地（未検証・L-4 で確認予定）**

Web Push 自体は Access の影響を受けない（サーバ → FCM/APNs → 端末）。しかし通知をタップした
あとの `/worktrees/<id>` は Access を通るため、セッションが切れていると**ログイン画面に着く**。
実運用上「対応が必要なときにすぐ対応できない」ことになりうる。L-4 で確認する。

**F. 合格だが気になった点 — roster の `AUTO_YES` 列**

`commandmate auto-yes --instance claude-2 --enable` の直後、`commandmate instances` の
`AUTO_YES` 列は `no` のままだった。セッション未起動のため `capture` の `autoYes` も `null`。
セッション起動後は `{"enabled": true}` になり、ゲートも正しく効いたので**動作は正しい**が、
**画面上は「有効にしたのに no」と読める**。表示と実体の乖離として記録する。

`created_at`(00:20:19) と `updated_at`(00:21:34) の 75 秒差からしか特定できなかった。
`route.ts` は `push-subscription-patch-failed` しかログしない。

切り分け中、無関係な `commandagent-develop` のエスカレーション再通知が繰り返し飛び、

#### 電池消耗・発熱の切り分け（Epic #2002 の前提確認）

**測定 1（希釈された窓・判定不能）**

| 時刻 | 残量 | その間の通知 |
|---|---|---|
| 17:19 | 88% | — |

| 17:29〜18:43 | | **0 通**（ログで確認。74 分間の無音） |

| 18:47:37〜18:48:27 | | 6 通 |

**H. iPad のカードが「ラウンドをまたぐ」と 2 枚になる（未解明・要追試）**

T-2 で iPad が 2 枚になった。だが追加測定では同じ経路が **1 枚 → 1 枚**で通っている。
待機通知も置き換え通知も **タグは同一**（`${worktreeId}:${kind}` = `commandmate-uat-push:prompt`）
なので、タグだけを見れば **どちらのラウンドでも置き換わるはず**である。

**唯一はっきりしている差は、直前のカードからの経過時間である。**

| | 直前のカードからの間隔 | 結果 |
|---|---|---|
| T-3 → T-2 | **3 分 14 秒**（00:20:49 → 00:24:03） | **2 枚** |
| 追加測定 | **43 秒**（00:29:17 → 00:30:00） | **1 枚** |

**仮説**: iOS は配信済み通知を一定時間で「置き換え可能な集合」から外し、
`getNotifications({tag})` にも返さなくなる。そうであれば `close()` も tag 置換も
古いカードに届かず、新しい 1 枚が積まれる。

**この仮説はまだ n=1 ずつであり、確定していない。** 確かめるには
**間隔を意図的に 3〜5 分空けた往復**を、0 枚から始めて数回回す必要がある。

**実運用への影響は小さくない。** 現実の待機は数分〜数時間おきに起きるので、
**失敗した側の時間帯こそが通常運用**である。設計書 §7 は
「`getNotifications()` が効かなくても tag 置換が救うので片肺にならない」と書いているが、
**両方とも時間で失効するなら、その救済も時間依存**ということになる。

### H の続き（T-8 実施時の観測で仮説が入れ替わった）

T-8（14:21〜14:23）で 3 通が同一タグで飛び、**Android は 1 枚に畳んだが iPad は 2 枚**になった。

```
14:21:39  待機通知
              ↓ 47 秒
14:22:26  再観測 push（再起動後）
              ↓ 24 秒
14:22:50  置き換え push（resolution）
```

利用者の報告: iPad は **「4 分前 = 応答待ちです」** と **「3 分前 = 対応済みです」** の 2 枚。
`14:21:39` と `14:22:26` は**分単位では両方「4 分前」に丸まる**ため、
生き残った待機カードがどちらかは**この観測では区別できない**。

**だが決定的な事実が 1 つ取れた**: **置き換え push は直前の待機カード（24 秒前）を置き換えず、
新しい 1 枚を足した。**

| 間隔 | その時点の prompt カード数 | 置き換え |
|---|---|---|
| 43 秒（追加測定） | **1 枚**（0 枚起点） | **成功** |
| **24 秒（T-8）** | **おそらく 2 枚** | **失敗** |

**短い方が失敗している。経過時間では説明できない。**
§5.4 H の当初仮説（iOS が一定時間で置き換え可能集合から外す）は**この観測で否定される。**

### 差し替えた仮説: 同一タグのカードが 2 枚あると置き換えが壊れる

**iOS は同一タグの「最新の 1 枚」しか置き換えないのではないか。** この筋なら全観測がつながる:

```
14:21:39  待機      → カード A
14:22:26  再観測    → A を置き換えられず カード B が増える（2 枚）
14:22:50  置き換え  → 最新の B だけを置き換える → A + 置き換え済み B = 2 枚
```

43 秒の追加測定が成功したのは **0 枚起点でカードが 1 枚しか無かったから**であり、
T-2 の 2 枚も **前ラウンドの残骸が既にあった**ことで同じ説明がつく。
**Android は同条件で 3 通を 1 枚に畳んでいる**ので、エンジン差である。

|---|---|---|
| **H-1** | 0 枚 → 待機 1 通 → **4 分待つ** → 置き換え | **1 枚なら時間は無関係**（当初仮説の最終否定）／2 枚なら時間も効く |
| **H-2** | 0 枚 → 待機 1 通 → **47 秒後にもう 1 通**（同タグ）→ 数える | **2 枚なら prompt 同士の置き換えが失敗**＝差し替えた仮説が正しい |

**H-2 が本命。** これが 2 枚なら「iPad は同一タグを 1 枚に保てない」が根本で、
`getNotifications()` も tag 置換も**重複には無力**ということになる。
設計書 §7 の「1 が成立しなくても tag 置換が救うので片肺にならない」という想定が崩れる。

### H-2 実施（2026-08-30）— 原因確定、Issue #2155 を起票

```
00:00:37  待機通知        delivered:2 / failed:0
              ↓ 77 秒
00:01:54  再観測の待機通知 delivered:2 / failed:0
```

両端末 0 枚起点。**解決 push は混ざっていない**（`resolution-push-sent` なし）。

| 端末 | 結果 |
|---|---|
| **Android** | **1 枚**（畳まれた） |
| **iPad** | **2 枚**（積まれた） |

**同じ 2 通を受けての差なのでエンジン差。** 差し替えた仮説（同一タグの重複で壊れる）は
方向としては正しかったが、**原因はさらに手前だった。**

### 原因は「経路」であって時間でも重複でもない

`public/sw.js:228-232` は、明示的な `getNotifications({tag})` → `close()` を
**`resolved: true` の解決 push にしか通していない**。通常の待機通知は
**ブラウザ任せの tag 置換**に頼っており、**それが iOS で機能しない。**

| 観測 | 経路 | iPad |
|---|---|---|
| prompt → resolution（43 秒） | `replaceStaleNotifications`（close→show） | **1 枚** |
| prompt → prompt（77 秒）＝ H-2 | `showNotification` のみ | **2 枚** |
| prompt → prompt → resolution ＝ T-8 | 混在 | **2 枚** |

**24 秒で失敗し 43 秒で成功していた**ことが、時間仮説を否定したうえで経路仮説を支持する。

### 設計書 §7 の想定が逆だった

§7 は「`getNotifications()` が iOS で効かなくても、tag 置換が救うので片肺にならない」と
書いているが、実測は逆で、**`getNotifications()` / `close()` の方が動き、tag 置換が動かない。**
close 経路を通らない通知は iOS で救われない。

**実害**: エスカレーション再通知（`waiting-push-notifier.ts:260`）は `escalated: true` の
通常 push なので close 経路を通らない。しきい値 5 分で 1 時間放置すると **iPad に最大 12 枚**積まれる。
再起動による再観測も同じ。そして T-8 で実測したとおり、**解決 push は最新 1 枚しか置き換えない**ので
古い「応答待ち」は残る —— #2001 が解決しようとした不満そのもの。

**H-1（4 分間隔の時間検証）は不要になった** — 時間仮説は H-2 が否定した。

**Issue #2155 を起票済み。**

**I. `push-fanout-complete` に `worktreeId` が無く、どの待機の通知か判別できない**

T-4 の最中に `mycodebranchdesk` / `claude-3` の通知が 2 通混入した。
`push-fanout-complete` のログは `{kind, delivered, failed}` だけで **どの worktree 宛かを持たない**ため、
同時刻の `resolution-push-sent`（こちらは `worktreeId` を持つ）と突き合わせないと切り分けられない。
解決 push を伴わない待機通知の場合は突き合わせる相手すら無い。

**UAT では「通知が来ないこと」を確かめる項目（T-4 / T-6 / T-7）が複数あり、
そこに他ワークツリーの通知が混ざると誤判定に直結する。**
`push-fanout-complete` に `worktreeId` / `instanceId` を足すだけで解消する。

**J. 待機通知の本文が「最初の分類」で固定され、実態と食い違う**

T-7 の待機通知は iPad に **「端末の確認が必要です」**（`terminalAttention`）と表示された。
だがサーバ側の `waitingKind` は **`prompt`** であり、本来は **「応答待ちです」**
（`promptWaiting`）が正しい。

```
00:08:38.837  ask-user-question-recorded / pre_tool_use: AskUserQuestion
00:08:39.704  push-fanout-complete            ← 0.9 秒後。まだ画面が確定していない
00:08:44.863  notification: permission_prompt ← 約 5 秒後に分類が prompt へ落ち着く
```

`needsTerminal()` は `waitingKind` が `'menu'` か `'unclassified'` のとき true を返す
（`push-sender.ts:239-241`）。**push は最初の観測＝まだ `unclassified` の時点で組まれる**ため、
本文が terminal 側に倒れる。その後 `observeWaitingEdge` は
`existing.kind = kind` で種類を更新するが **再 emit しない**ので、
**カードの文言は誤ったまま固定される。**

**これは文言の揺れではなく、読者が取る行動を逆に指示している。**
`needsTerminal` の docblock 自身がそう書いている:

> A `menu` … and an `unclassified` wait share the one fact the reader acts on:
> **tapping the notification will not present anything to answer.**

実際にはタップすれば答えられる。**「端末へ行け」と言われた読者は無駄足を踏む。**

**間欠的である**: T-1 / T-8 では「応答待ちです」が正しく出ていた。
push と分類確定の競走なので、**送信が速いほど外れる。**

**#2155 と重なると悪化する**: iOS では後から正しい文言に置き換えることもできない。
