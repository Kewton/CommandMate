- **chore(orchestrate): リーダーが直接流した verify を run 番号から run-log に env つきで記録する `run-log.mjs record-verify` を追加** (#4482): wait-verify はワーカーの合図を待つため、リーダーが `commandmatedev verify <wt>` を直接流した run は run-log に手で `verify=ok` と run 番号を書くしかなく、`env=` が残らなかった（Sprint 7 の A1〜D2）。`record-verify --run <id> --wt <worktree id> --worktree <path>` は `verify show <id> --json` を読み、run の事実だけを写す: `passed` だけを `verify=ok`、`failed`・`error`・`cancelled`・`not_started` を `fail`、ゲートごとに `gates=<id>:<ok|skip|fail>`（読む人のための欄で、precheck・merge-pr のゲートの再利用には使われない）。`running`・`queued` の run は結果を決めずに exit 3 で断る。run は HEAD を持たないので、**head はその run が確かめた木と同じだと言えるときだけ書く（fail-closed）**: 未コミットの変更が無い（`dirtyPaths`）、HEAD のコミットも HEAD の reflog の最新の移動（`git log -g -1 --date=unix --format=%gd HEAD`）も run の開始より前、`--worktree` が `ls --json` の `--wt` の path と realpath で一致、env の入力（settings・lockfile・node_modules）の mtime が run の開始より前、のすべてを満たさなければ、または run の worktree・id・task の不一致・記録済み・読めない値があれば exit 4 で何も書かない。env は記録する時点の manifest（note の `env-at=record`）で、`env-manifest.mjs` の `manifestHash` で `env=<hash>` を書き `verify-<work item>.run<id>.env.json` に置くので、precheck / publish / merge の `verifyEnvState` は wait-verify の行と同じに照合する。`--task` は照合だけに使い run に task が無ければ書かない。wait-verify の記録の形と `append` / `status` は変えていない。
