# 1-2b の根拠と実測

1-2b（難易度判定と担当割当）の判定表と規則は本体にある。ここには、その根拠と実測を移した（#3481）。

## 1-1 OPEN の Issue が着地済みのことがある

Issue が OPEN でも未着手とは限らない（本体が別の PR でマージ済みで、閉じ忘れていることがある）。Phase 1 で Issue ごとに `gh pr list --repo Kewton/CommandMate --search "<番号>" --state merged` を実行し、着地済みなら残りのギャップだけを対象にして、その前提をワーカーにも渡す。本文が `cmate-*` の skill を名指ししていたら、修正先は skill の配布元の別リポジトリのことがある。着地の判定は Issue の記述ではなく、そのリポジトリの実コード（`git grep <新しいコード> origin/main`）で行う。

## 1-2b 重複の報告の行き先の根拠

実測（#3208、2026-10-04 の集計）: 2026-09-01 以降に `src` を変えた fix・feat・refactor 322 本のうち、refactor は 12 本だった。
「重複は直さずに報告する」と決めていたが、報告された重複を整理の Issue にする段が、手順に無かった。

退避路が決めているのは「直さずに報告する」までである。報告の行き先が無いと、重複は残り続ける。ワーカーが「本文に無い指摘」で同じ処理の写し（重複）を報告したら、その run では直させず（整理と振る舞いの変更を同じ PR に入れない。2-4-3）、オーケストレーターが `workspace/orchestration/runs/$DATE/refactor-candidates.md` に 1 件 1 行（報告した Issue・`file:line`・何と何が写しか）で残し、run の最後に整理の Issue として起票するかを利用者に訊く（8-4）。

## 1-2b 件数をやめて判断の余地にした根拠

**「件数」をやめて「判断の余地」にした根拠（2026-09-20、Epic #2735 / #2740 の 9 Issue）**:
旧ルールの「影響ファイルが 4 件以上 → 難」は、**同じ run の中で 2 本を誤判定した**。

| Issue | 影響ファイル | 旧ルールの判定 | 実際（Antigravity） |
|---|---|---|---|
| #2733 | **7** | 難 | 再指示 0・全ゲート初回 PASS |
| #2737 | 4 | 難 | 再指示 0・全ゲート初回 PASS |
| #2739 | 3 | 易 | 再指示 0・全ゲート初回 PASS |

3 本とも確定 diff ＋ 退避路つきで、**3/3 が一度で通った**。一方、同じ run で唯一往復したのは
Claude 担当の #2734（4 ファイル）で、その原因も**起票時の前提の誤り**であってワーカーの実装ではない。
**ファイル数は難易度を予測していない**（逆相関すらしている）。#2616 の例（6 ファイルで「難」判定 → 実際 4.5 分）も同じ向きの反証である。

過去に Antigravity で起きた事故も規模由来ではない: #2605 はテスト全体をバックグラウンド実行してターンを閉じた（道具の問題）、
#2622 は受入基準に「確かめる場所」を書かなかったので本物の `$HOME` を消した（**仕様の書き方**の問題）。

**上げた境界と、上げていない境界**（2026-09-20 実測）:

- **上げた**: 確定 diff を N 件適用（件数無制限）、および**既存ガードへの assert 追加・書き換え**。
  #2739 は #2734 が完全一致で pin していた既存 assert を壊さずに書き換えており、これが成立した
- **上げていない**: 150〜280 行の**新規ガードを 1 本まるごと書く**（#2732 / #2734 / #2736 型）。
  override を構造で特定する・陽性/陰性対照を設計する、は設計判断であり根拠がない

**「設計」と「転記」の線引き（2026-09-20 実測、3/3）**: 上の「上げていない」境界は
**ワーカーが設計する**場合の話である。**本文にテスト全文が載っていれば、ワーカーがするのは
`git apply` か写経であって設計ではない**。実測:

| Issue | 新規ガードテスト | 担当 | 結果 |
|---|---|---|---|
| #2770 | 32 件（本文に全文） | antigravity | 再指示 0・全ゲート初回 PASS |
| #2780 | 7 件（確定パッチに全文） | antigravity | 再指示 0・全ゲート初回 PASS |
| #2781 | 13 件（確定パッチに全文） | antigravity | 再指示 0・全ゲート初回 PASS |

#2781 のワーカーは、変異注入 1 と 2 が**独立して fail すること**まで確かめている
（起票側がプロトタイプ段階で見つけて直した弱点そのもの）。指示どおりの検証ができている。

**全文を書くコストは起票側が負っている**ので、この線引きは判定を緩めるのではなく、
**コストの所在を判定に反映させる**ものである。全文が無い Issue は従来どおり「難」のままとする。

## 1-2b 委任する Issue で起票側がやること

この節は判定を変えない。Command Code（易・中）の条件は本体 1-2b の表のとおり、**選択肢か手順と受入条件が本文で閉じている**ことである（2026-11-19 改定。易は置換後のコードまで、中は選択肢か手順と受入条件まで）。本文が閉じていない Issue は、イネーブラーが「選択肢・手順・受入条件」まで具体化してから着手する。閉じないもの、または難の観点に当てはまるものは Claude（opus）に回す。次はその Claude に回す Issue を起票するときの書き方である。

起票側は判断だけをする: 根本原因の特定（再現 1 回で足りる）、方針と不変条件、変更箇所（file:関数）とインターフェース、受入基準（入力の形と期待する結果）。実装・テスト本文・全件走査・変異の確認はワーカーに任せ、受入基準で縛る。試作が要るのは方針の成否が実測しないと決まらないときだけで、その 1 点を最小で確かめる。前提が怪しい箇所は「外れたらこの代替」まで書く（「変更せず報告」の退避路は前提が外れると守られないことがある）。「〜の経路にも効く」と書く前に入口の関数から呼び出し経路を 1 本たどる。

## 1-2b 易の Issue を起票するときの書き方

Command Code に回す（易は全変更の置換後のコードまで、中は選択肢か手順と受入条件まで本文で確定させる）と決めた Issue の書き方。上の「上げた境界」（確定 diff を件数無制限・既存ガードへの assert の追加と書き換え）は易と判定してよい範囲で、ここの項目はその範囲を狭めない。

- 方針は案を並べず 1 つに決めて書く。方針の成否にかかわる一点（例: jsdom が捨てる CSS 関数）だけは起票の前に実測する
- 受入基準には合否が自動で決まるもの（lint / typecheck / unit / e2e）だけを入れる。CI・PR・本番で確かめる項目と見た目の確認は「オーケストレーターが確認すること」節に分ける
- 確定 diff の件数・ファイル数では Issue を分けない（判定は件数を問わない）。分けるのは、同じファイルを触る別の Issue との依存（1-4）など、件数以外の理由があるときだけ
- 同じファイルを触る Issue を並べて出すときは、確定パッチを 1 つのコピーに両方の順で当てて `git apply --check` で通ることを確かめる
- Issue 本文の上限は 65,536 文字（バイトではない）。確定 diff とテスト全文を貼ると近づく

## 1-2b 2026-11-19 に変えた理由と、変えた後に測るもの

**変えたこと（2026-11-19、人の決定 mem 9480db9b）**:

- Command Code に回すのは、難の観点（危険な領域・設計・原因未特定・未決事項・実機でしか決まらない検証・強い依存・新規 export）に当てはまらないもの**すべて**。旧「中」のうち、選択肢か手順と受入条件が本文で閉じている**判断**も Command Code に入れた（新しいガード・テストを 1 本まるごと設計するものは難＝opus のまま）
- 条件を「変更する全箇所が `file:line` ＋置換後のコードまで確定」から「**選択肢か手順と受入条件が本文で閉じている**」に替えた（易は従来どおり置換後のコードまで）
- Command Code がワーカー起因で 2 回不合格なら **opus**（3-5）。sonnet は Command Code が起動・送信で詰まったときの代わりだけ（理由を lead-return に書く）
- 格上げの条件と同じ種類の指摘の 2 回目の両方に当たるとき: [roles/dev-leader.md](roles/dev-leader.md#難易度とワーカー)
- 着手の前に、イネーブラーが Issue を「選択肢・手順・受入条件」まで具体化する段を置く
- 目標は仕事の **6〜8 割**を Command Code で回すこと（Sprint ごとにワーカーのモデルの割合を lead-return と台帳に数える）

**変えた理由**:

- 目標の 6〜8 割に対して、全箇所の置換後のコードまで本文で決める起票コストが高すぎた。旧「中」は結論が作業の前に決まっているので、本文が閉じていれば Command Code でも判断の余地は残らない
- **難の観点は緩めていない**。危険な領域（tmux・セッション・detection・polling/Auto-Yes・hooks・security・DB migration・cli-tools・ws-server）と、設計・原因未特定・未決事項・実機の検証・強い依存・新規 export は、従来どおり opus に残す
- 易を確定 diff に限った根拠（#2605・#2622 の**道具の事故**）は、本文の閉じ方の話ではない。だから危険な領域を Command Code に下げないまま、閉じた判断だけを Command Code に移せる。確定 diff の誤りが易の前提を崩す例（#2936）も、易では従来どおり確定 diff を要ることで残す

**変えた後に測るもの（8-2・8-3、lead-return、台帳）**:

- 中として Command Code に回した Issue ごとの**再指示の回数・格上げの有無**と、どの条件で中にしたか

- 判定表と実際の結果の食い違い（「易・中」で再指示が要った／「難」が小さく終わった）
- 3-5 の格上げ（Command Code → opus）の回数と、失敗したゲート

## 1-2b 易しい bug の速い道

元の場所: team.md §6 の 10（#4546 で移した。文は元のまま）

対象は易・局所（1〜2 ファイル）で、2 の 5 つ（送信の経路と relay・ロック・データ（migration・DB の書き込み）・公開の API と CLI の契約・ゲートと検証の定義）に触れないもの。流れは設計の段を省き、Command Code のワーカー → レビュー 1 本 → verify（ゲートは 1 つも変えない）→ CI 全件 success → `--last`。受け入れはリリース前のまとめで拾う。迷ったら通常の流れ（高リスクの規則）に戻す。速い道にした Issue は返しに「速い道」と書く
