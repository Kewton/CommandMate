- **fix(relay): 不確定な配送の保留（`uncertain`）を解決する操作を追加し、旧試行の遅い結果が新しい試行を閉じないようにする** (#4082): #4064 で保留にした relay の payload は取消しか手が無かったため、`POST /api/relays/:id/resolve`（本文 `{ payloadId, attemptId, action: confirm | retry | discard }`）と `commandmate relays resolve <relay-id> --payload <id> --attempt <id> --confirm|--retry|--discard`（どれか 1 つが必須）を追加。解決は relayId・payloadId・attemptId・`delivery_state='uncertain'` の一致を条件にし、閉鎖・本文の消去・後続の返答の繰上げを 1 つのトランザクションで確定する（途中の DB 失敗は全部戻して 500）。返答（open）は confirm で `delivered`・retry で同じ payload を配送の列へ・discard で `cancelled`（両スロットを消す）、確認の通知（open）は confirm・discard で保留を消して待っていた返答を同じトランザクションで繰り上げ（`prompt_signature` は残すので同じダイアログは再通知しない）・retry で列へ、期限切れの通知は閉じたまま confirm・discard で消し retry で列へ。取消・期限切れで閉じた relay の返答・確認の通知は confirm・discard だけ許し（閉じた理由は変えない）、retry と期限を過ぎた relay の retry は 409。古い試行・二重操作・配送中（`attempting`）・保留なし・試行 ID の無い保留も 409 で何も変えず、relay 無しは 404、不正な本文は 400。confirm・discard は打鍵 0 回、retry は「列に戻した」で送達ではなく、次の配送（readiness・所有権・入力ロックを通る）が 1 回だけ送る。あわせて `completeRelayReplyDelivery` が relay の閉鎖を試行の照合より先に実行していたため、別 boot の復旧で保留になった試行 T1 を retry して T2 が取った後に T1 の成功が戻ると relay を閉じて T2 の本文を消していた問題を修正（返答・確認の通知・期限切れの通知の結果の処理は、副作用の前に現在の payloadId・attemptId・`attempting` を確かめ、失効した結果では閉鎖・本文消去・繰上げ・system 行を行わない。確認の通知の完了と繰上げも 1 トランザクションに）。確認の通知を retry した後・配送の前に後の返答が完了したときは、保留中に第 2 スロットで待っていた返答を優先して第 1 スロットへ入れ、第 2 スロットも同じ書き込みで消す（後の返答は捨てる）。解決の応答に載せる relay の読み取りも確定の前に同じトランザクションで行う（読み取りが失敗したら何も確定せず 500）。`relays --token T resolve|cancel …` の token と `relays cancel <id> --json` が親の `relays` に取られて効かなかった（token は `CM_AUTH_TOKEN` に落ちていた）のを修正。公開の `deliveryHold` に `attemptId` を追加（REST の全応答・CLI の JSON と通常表示の `attempt=`）。日英の手引きの「届いていなければ自分で送り直す」を解決操作の案内に置き換えた。migration は無し（v63 の列のまま）。
