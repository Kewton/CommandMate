- **fix(relay): 自分が開いた relay の返事を受けた後の次の依頼が `RELAY_CHAIN_BLOCKED` になる問題を修正し、代わりに往復の回数に上限を置く** (#4420): relay の返事は依頼元の履歴に `relay:<id>` の user 行として配送され、連鎖の判定（`findParentRelayHops`）がその行を次の relay の親に数えていたため、「送る → 返事 → 次を送る」の 2 回目が旗なしで `RELAY_CHAIN_BLOCKED`、`--allow-relay-chain` でも 4 回目で `RELAY_HOPS_EXCEEDED` になっていた。行が名指す relay の `from` が自分自身なら返事として親に数えず、その後ろの本当の親（自分が `to` の relay の行）は今までどおり探して hops を数える（窓は返事の分だけ広げ、同じ時刻の行は普通の行を新しい側に並べ、echo は直後の relay 行にだけ照合する）。返事を受けた直後に次の relay を開く往復は、人の普通の行を挟まずに `MAX_RELAY_ROUNDS`（10）回続くと既存の `RELAY_HOPS_EXCEEDED`（往復の上限と分かる別の文面）で断り、`--allow-relay-chain` では外れない。数えるのは依頼元セッション単位（相手を問わない）で届いた返事だけ（期限切れ・cancelled は数えず、期限切れの知らせは数えも 0 戻しもしない）、新しいコード・列・migration は無い。既知の制限: (a) 行に送り手が無いため、人以外の普通の行（relay なしの `send`・`flow tick` の 1 行など）でも往復の数は 0 に戻る（上限が緩む向き） (b) 依頼に答える途中で開く B→C の relay は、受け手の依頼の行に relay の印が無いため今も本番で止まっておらず、この変更でも変わらない（続きは #4492） (c) 人が返事と同じ本文を打ち直した行は #2387 の規則どおり echo と区別できない (d) 読む範囲（45 ターン）を使い切っても終わりの行に当たらないときは上限に達したとみなして断る。
