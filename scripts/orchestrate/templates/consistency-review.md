【依頼】Issue #{{ISSUE}} の修正を、「変更されなかった場所との食い違い」だけに絞ってレビューしてください（読むだけ。変更なし）

■ 目的
この修正を PR にしてマージしてよいかを決めたい。ふつうのコードレビューではありません。見るのは 1 点です。
「この変更によって、変更されなかった場所との間に、食い違いが生じていないか」
（整合性レビューの試行です。Issue #3308。あなたの指摘の数と、後で確かめた結果を記録します）

■ 対象
- 変更のある作業場所: {{WORKTREE}}（branch: {{BRANCH}}。HEAD: {{HEAD}}。この場所のファイルが、PR の状態です）
- 差分: `git -C {{WORKTREE}} diff origin/develop...{{HEAD}}`（コミットの説明は `git -C <同じパス> log origin/develop..{{HEAD}}`）
- Issue の本文と、ワーカーへの指示: {{WORKTREE}}/.commandmate/tasks/issue-{{ISSUE}}.yaml の goal
- コードは、上の作業場所のパスで読んでください（あなたの作業場所のリポジトリは、この PR の土台と同じ develop とは限りません）

■ 手順
1. 変更の要点を 3〜6 個に分ける（何を足した・直した・変えたか）
2. 要点ごとに、対になる場所を探す: (a) 同じ処理の写し（PC とスマホ、チャット面とターミナル、ルートどうし、ツールごとの実装、同じ関数を別の関数越しに呼ぶ経路）／(b) 同じ値・型の写し（サーバーの型と src/cli/types/、定数、辞書の ja・en）／(c) 説明（docs/ の ja と en、コメント、JSDoc）／(d) 古い動きを固定しているテスト（回数・文言・タイミング）／(e) 直した理由が、同じ場所の別の条件や別の枝にも当てはまらないか
3. 「該当する場所をすべて直した」という列挙は、別の方法（呼び出しの連鎖をたどる）で確かめ直す
4. 対のそれぞれについて、この変更で変えられたか、変えられていないなら食い違いになるかを判断する

■ 出力の形
全体で 60 行以内。
(1) 変更の要点（番号つき、各 1 行）
(2) 指摘（重い順に最大 6 件。無ければ「指摘なし」。無理に作らない）。各指摘は次の 5 行:
    - 題 / 種類 (a)〜(e) / 変更された側 file:line / 変更されなかった側 file:line
    - 何が食い違うか（1〜2 文）
    - 利用者に見えるか（どの経路で）
    - この PR の範囲で直すべきか、別の Issue か
    - 確信度（高・中・低）と理由 1 行
(3) 対として調べ、問題なしとしたもの（各 1 行、最大 8 件）
(4) 調べられなかったこと
重大度は P1（マージを止めるべき）／P2（この PR で直したい）／P3（別の Issue でよい）で書いてください。

■ 触ってはいけないもの
- ファイルを変更しないでください（どの作業場所でも）。レビューは返答の本文だけで返してください
- git の状態を変えないでください（checkout / pull / stash / commit / reset をしない）
- gh などネットワークを使うコマンドは使わないでください（必要な情報は、上のファイルにあります）
- push / PR 作成 / merge / Issue の作成・コメントは行わないでください
- サーバー・tmux セッション・テストを起動しないでください

■ 前提（あなたは知らないはずのこと）
- 実装したのは Claude のワーカーです。契約の検証（lint・typecheck、Issue によっては unit と integration）は通っています
- Issue の受入基準は goal の要約より Issue 本文（gh は使えないので goal と差分・コミット本文から読んでください）が詳しいです
- 推測で埋めないでください。確かめられなかったことは「未確認」と書いてください

最後に `DONE:` で始まる1行で結論を要約してください（例: `DONE: 指摘 2 件（うち、この PR で直すべきもの 1 件）`）。
