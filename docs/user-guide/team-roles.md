# チームの役割: PM・開発リーダー・ワーカー

リポジトリの指示書（`CLAUDE.md`、`AGENTS.md` など）に書く「役割の節」のテンプレートです。各セッションが自分の役割を知るために使います。特定のエージェント CLI には依存しません。[セットアップガイドの Stage 6](https://github.com/Kewton/CommandMate/blob/main/website/setup.md) がこれを使います（`commandmate docs --section setup` で読めます）。

`<...>` は置き換えてください。インスタンス ID は `commandmate instances <worktree-id>` で分かります。

## 3 つの役割のつながり

人が話す相手は PM だけです。PM は開発リーダーに頼み、開発リーダーが契約をつけてワーカーに作業を渡します。作業が終わったかどうかは、チェック（`commandmate wait <worktree-id> --instance <worker> --verify`）が決めます。

| 役割 | 話す相手 | すること | しないこと |
|------|----------|----------|------------|
| PM | 人、開発リーダー | 人の依頼をブリーフにし、進みを見て、報告する | コードを書く、ワーカーへ直接送る |
| 開発リーダー | PM、ワーカー | ブリーフを作業に分け、契約をつけて渡し、ゲートを待つ | 人へ直接聞く |
| ワーカー | 開発リーダー | 契約の範囲の中で 1 件を進めて commit する | 範囲外のファイルを変える、マージする |

## 各セッションに役割を伝える

指示書に役割ごとに 1 節を書き、各セッションに最初に `commandmate whoami` を実行させ（出るのは worktree・インスタンス ID・ツール・別名で、役割は出ません）、インスタンス ID を節と突き合わせて、自分の役割を自分の言葉で述べさせます。指示書に自分が見つからないセッションは、推測せずにそう伝えて止まります。

## PM の節（テンプレート）

```markdown
## 役割: PM（インスタンス `<pm-instance>`）

- あなたは人と話す役です。コードは書かず、リポジトリのファイルも編集しません。
- 仕事は開発リーダー（`<lead-instance>`）に `commandmate ask <worktree-id> "<ブリーフ>" --instance <lead-instance>` で頼みます。ワーカーへ直接送ってはいけません。
- ブリーフは 4 点: 目的、Issue または対象ファイル、変えてはいけないもの、「終わり」の定義（verify のゲート）。
- 人への報告は下の型で書きます。承認と判断は人のものです。
- マージは人がします。（人が委任を選んだときだけ: head が検証したコミットと同じで、ゲートが全件合格し、CI が green で、レビューに blocker が 0 のときだけマージ。欠けたら人へ返す。ゲートや判定を緩める変更は常に人へ。）
```

## 開発リーダーの節（テンプレート）

```markdown
## 役割: 開発リーダー（インスタンス `<lead-instance>`）

- PM（`<pm-instance>`）からブリーフを受けます。人へ直接聞いてはいけません。質問や承認が要るときは PM へ返します。
- 作業ごとに `commandmate send <worktree-id> --contract .commandmate/tasks/<name>.yaml --instance <worker-instance>` で渡し、`commandmate wait <worktree-id> --instance <worker-instance> --verify` で待ちます。
- `wait --verify` の終了コード（0 合格、20 ゲート不合格、21 判定する作業がない）と、落ちたログの末尾を報告します。通すためにゲートを緩めてはいけません。
```

## ワーカーの節（テンプレート）

```markdown
## 役割: ワーカー

- 契約の 1 件を、その範囲の中だけで進めます。終わったら commit します。
- 範囲外のファイルが要るときは、そのファイルを変えず、気づいたことを commit メッセージに書いて止まります。
- 契約が求めないサーバーやバックグラウンドプロセスを起動しません。
```

## PM の報告の型

1 行目で、人が対応する必要があるかを、続きを読まなくても動ける 1 文で言い切ります。

- 「いまご対応いただくことはありません」
- 「ご判断いただきたいことが 2 つ残っています」

そのあとに何が起きたかを書き、判断事項はどれも、選べる選択肢（おすすめを先頭）で示します。

```text
ご判断いただきたいことが 2 つ残っています。

完了: Issue #12 は全ゲート（lint, unit）に合格。PR を作成済みで CI は green です。

1. PR #34 をマージしますか？  (a) マージする  (b) レビューを待つ
2. Issue #13 に新しい依存が要ります。  (a) 許可する  (b) 別の方法を探す
```

## 期限つきの自走

人が席を外す間も PM に進めさせたいときは、絶対の終了時刻とタイムゾーン、してよいこと、止まったときの報告を渡します（「今日の 09:30 JST まで進めてください。してよいのはチェックの実行と PR の作成だけです。止まったら、終わったことと残りを報告してください」）。Auto Yes も同じ期限に合わせます。

```bash
commandmate auto-yes <worktree-id> --enable --duration 3h --instance <pm-instance> --stop-pattern 'DONE:|BLOCKED:'
```

`--duration` は 1h〜24h の整数時間です。期限までに終わるものを選びます。`--stop-pattern` は端末出力に対する正規表現で、一致したら Auto Yes を早めに止めます。コマンドの実行は禁止できないので、権限の境界ではありません。

## 承認は人のもの

セットアップを進めるエージェントは、人の代わりに承認もマージもしません。既定は人がマージします。条件つきの委任は製品のスイッチではなく、人が選んだときだけ、上のように PM の指示書へ書く運用ルールです。
