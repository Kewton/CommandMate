## 2-4-1 断片方式にした理由

**なぜこうするか（2026-08-22 の実測）**: 全ワーカーが `CHANGELOG.md` の同じ節に追記すると、
**1 本マージするたびに残りの PR が全部 CONFLICTING になり、refresh → CI 全周やり直しが必要**になる。
CI は中央値 38 分（self-hosted 1 台・11 ジョブ、同時 5〜6 本なら 55 分）なので、
N 本のマージが N 回の直列 CI に化ける。実測では PR 21 本に対し CI 53 回（1 PR あたり 2.5 回）で、
やり直しの大半がこの結合に起因していた。断片方式なら PR 間の強制直列がほぼ消える。
2026-09-18 に、CHANGELOG の断片はコミットする方式に移った（#2640 / #2641）。オーケストレーターが 6-4 で `CHANGELOG.md` へ
書き写す方式では、書き写した PR をマージするたびに残りの PR が `## [Unreleased]` で衝突していた（2026-09-17〜18 の run で計 7 回、手で解消）。

## 2-4-1 実例を丸ごと貼る理由

**実例を丸ごと貼る理由（2026-08-22〜23 の実測）**: 形式を上の 1 行の抽象仕様だけで示していた Phase 4 では、
**4 ワーカー中 3 つが形式から外した**（#1930 は `- 構造化層の状態導出を…（Issue #1930、Epic #1921 Phase 4）`、
#1931 は `- opencode の SSE / REST 経路が…（Issue #1931）。`、#1933 は要約と Issue 番号をまとめて `**…**` の中へ入れた）。
規約どおりだったのは #1932 だけで、3 本ともオーケストレーターが一本化時に書き直している。一方、契約に実例を
丸ごと 1 本貼った #1994 の断片は初回から規約どおりだった。**抽象的な形式指定では守られず、実例なら守られる。**

module-reference 側は**実例だけでは足りない**（判断の根拠つき）。#1927 と #1932 の契約には既に
「`grep -n '^| \`<path>\`' docs/module-reference.md` で実在を確認してから書く」が入っていたのに、
**存在しない行への追記指示が #1927 で 4 件・#1932 で 1 件**出た（オーケストレーターが一本化時に裁定）。
CHANGELOG 側が**形式**の誤りで断片を見れば分かるのに対し、こちらは**事実**の誤りなので断片を読んでも分からない
──手本を足しても検出できる誤りが増えない。そこで指示を「確認する」から**「確認した出力（行番号つきの行キー）を
断片に書き写す」**へ変え、6-4 で断片を `cat` した時点で証拠の無い追記指示が目に見えるようにした
（**6-4 の手順自体は変更していない**。既存の `awk … uniq -d` は行が 2 本になった後しか捕まえられないが、
証拠の有無は写した瞬間に読めるので手順を足す必要が無い）。なお実在確認は**転記ブロックには入っていなかった**
（実測: 変更前の `.claude/commands/orchestrate.md` に `grep -n` は 1 箇所も無く、上記 2 本の契約は
オーケストレーターが手で足していた）ので、あわせて転記ブロックへ引き上げた。

契約の起案側は、断片の確認に使う grep の対象を列挙しない。ワーカーは列挙されたものだけを引くので、列挙の漏れがそのまま断片の「追記なし」になり、断片を読んでも分からない。「変更したファイルすべてについて行キーを引く」と書き、rename を含むときは旧名でも引かせる。6-4 ではオーケストレーターも同じ grep を独立に引いて突き合わせる。

## 2-4-2 雛形の実例と外のファイルを消した件

実例: パイロットの契約（#2595）は、この雛形のとおりに書いて一度で通った（goal は 3,282 文字。上限は 8,000 文字）。
Antigravity は、雛形にあるルールのうち次のものをすべて守った:
1 コミット・指定したメッセージ・scope 内・断片の形式・push/PR をしない・`IMPL_COMPLETED`・一時ディレクトリでの陰性対照。

**「worktree の外の既存ファイルを消さない」を書く理由**（2026-09-17 #2622）: #2622 は、テストが `$HOME` と `/tmp` に
ファイルを残す不具合だった。Antigravity は修正を確かめるために、残っていた本物のファイル
（`rm -f ~/.commandmate/hooks/claude-wt-1933-…json`、`rm -rf /tmp/cm-1933-worktree`）を消し、テストを実行して
再び作られないことを見た。確認の手順としては筋が通っているが、worktree の外の既存ファイルを消す操作であり、
goal では頼んでいなかった（goal の受入基準に「`/tmp/cm-1933-worktree` に何も残らない」と書いたことが、消す動機になったとみられる）。
scope ゲートは worktree の外の操作を見ないので、こうした操作は検証では捕まらない。今回は、消したのが不具合の残骸だけだったので害は無かった。

## 2-4-3 置き場所と同期の理由

**新しいモジュールに置く理由**: テストは、モジュールをパスで差し替えている。

## 2-2 依存が欠けた worktree の見分け方

`node_modules` があっても中身が欠けていることがある（中断したコピー・install）。存在チェックでは見分けられない。

- 兆候: ワーカーの tsc に `Cannot find module 'fs' / 'path'`・`Cannot find name 'process'` が大量に出て、`tsconfig.json` の `include` に無いファイルまで発生源に並ぶ。自分のコードを疑う前に `ls node_modules | wc -l` を主のチェックアウトと比べる（1〜2 件の差は hoisting で無害、桁違いだけを異常と見る）
- 数が揃っていても 1 パッケージだけ部分的なことがある。`for d in */ @*/*/; do [ -f "$d/package.json" ] || echo "MISSING: $d"; done` で `package.json` の無いものを探す（lint・tsc・unit は通り、`npm run build` だけが落ちる形がある）
- 直したらワーカーに「大量の未解決は環境起因だった、npm install は不要」と伝える

## 2-4 生成器が止まる条件

- 生成器は、出力する契約を正準のパーサー（`src/lib/tasks/contract-parser.ts`）と同じ制約で検査する（title 200 文字・gate の形と重複・scope の形）。
- **goal が 8,000 文字を超えると生成が失敗する**（契約の上限）。Issue 本文を要点に縮めた `issueBodyFile` を渡し直す。検査するのは parser が数える文字列と同じで（末尾に改行を足さない。YAML は `|-`）、ちょうど 8,000 文字は生成も送信も通る（#4135）
- `scope` に `CHANGELOG.md` / `docs/module-reference.md` を書くと生成が失敗する（2-4-1）。`requireCommit: true` は常に入る
- 同じ設定で再実行しても契約は変わらない（`unchanged`）。中身の違う契約が既にあると止まる。送信前に直すときだけ `--force`
- `agent` は `claude` か `command-code`（易、#4238）。`agent: antigravity` は契約を作らず、`command-code` に置き換えた旨を出して止まる（exit 1）。`command-code` に `model` は書かない（docs/orchestrate/command-code.md）

## 2-4 src を触る契約の build-server

`typecheck`（`npx tsc --noEmit`）は `tsconfig.json` だけを読み、`lib` は `esnext`。サーバーのビルドの `tsconfig.server.json` は `tsconfig.base.json` の `ES2022` までで、`include` も別にある。
だから「サーバーのビルドだけで落ちる型エラー」は `typecheck` を通る。実例（#4124）: #4114 のコードが #4115 で初めてサーバーのビルドに入り、`isWellFormed` が CI の `Build` で落ちた。

決定（#4135）: 新しいゲートは足さず、既にある `build-server` を、生成器の既定に入れる。`gates` を省略し、scope が `src/` の下か `server.ts`・`tsconfig.server.json`・`tsconfig.base.json` に届くときだけ `[lint, typecheck, build-server, unit-related]` になる。「届く」は scope ゲートの意味（`src/lib/verification/scope-gate-glob.ts`）で読む: `src` 単独、`**/*.ts`、`{src,docs}/**` も届く。

`--worktree`（省略時はカレントディレクトリ）の `.commandmate/verify.yaml` に `build-server` が無ければ足さない。`POST /tasks` が未知のゲートを 400 で拒否し、従来の既定で送れていた契約が送れなくなるため。

| 実測（2026-11-04、この worktree・warm、load average 30〜41） | 所要 |
|---|---|
| `npm run build:server` 3 回 | 3.63 / 3.65 / 3.33 秒 |
| `npx tsc --noEmit` 1 回 | 24.19 秒 |

既定に入れても検証の時間はほとんど変わらない。

- `gates` を書いた設定は書いたとおりに走る（生成器は足さず、verify.yaml も確かめない）。本体の雛形が `build-server` を書くのはそのため
- `kind: refactor` の既定は `[lint, typecheck]` のまま（テストが固定している）。CI の `Build` を待つので、マージの前には検出する

- `.claude/skills/<name>/**` を scope に書くとき、`.agents/skills/<name>/` に写しがあるスキルは `.agents/skills/<name>/**` も対で書く（`contract.mjs` は足さない）。`tests/unit/skills/<name>/mirror.test.ts` が両者のバイト一致を固定しているので、片方だけだと「写しを直して scope が赤」か「直さず unit が赤」になる。fixture や `.sh` を足すスキルは、ファイル一覧を固定する `mirror.test.ts` と `.sh` の本数を数えるテストも scope に入れる。scope の FAIL を見たら、まず `diff -rq .claude/skills/<name> .agents/skills/<name>` で写しが同じかを確かめてから裁定する
- Issue が「prop で渡す」と書いていても、間の親が子の props を `useMemo(() => ({…}))` の 1 つのオブジェクトとして自前で組んでいると、その親を編集しないと値が届かない。チャット面の `live`（`ChatSurfaceLiveState`）に値を足す Issue は、`src/components/worktree/TerminalSplitPaneContent.tsx` と `src/components/worktree/MobileTerminalTab.tsx`（セッション一覧なら `src/components/sessions/SessionTile.tsx`）を scope に入れる。起案時は消費者から親へ 1 段ずつ `grep -n '<Component' -A 20` で辿って確かめる。親を scope に入れられないときは、消費側が既に受け取っている生データ（`frame` など）から同じ述語で導き `live.<flag> ?? predicate(frame)` にするか（`||` ではなく `??`）、scope 内の共通祖先に context を置く（先例 `src/contexts/WorktreeChatSendContext.tsx`）

## 2-4 文面を変える契約と integration

## 2-4 本文の原因が未実測のとき

Issue 本文の原因が実測していない仮説なら、goal に「本文の機構の説明は実測していない仮説である」と書き、受入条件の第 1 項を「変更の前に事象を再現し、失敗の機構を実測で確定する。本文の仮説が正しいかどうかを書く」にする。「実測を正とする」とだけ書くと、ワーカーは着手した後で仮説に引きずられる。
本文に対照実験の表があっても、それが再現する保証は無い（測ったときと画面の中身が違う）。表がある Issue でも測り直させる。
`scope.allow` / `deny` を書くときは、本文の転記で済ませず実ファイルを引く。この作業で本文の事実の誤り（ファイルの場所など）が見つかる。

## 2-4 委任の前に本文の前提を確かめる

- Issue 本文の「決定」「実装者はこれに従うこと」のブロックも、契約に写す前に前提をコードで確かめる。「〜から遷移できる」「〜で判定できる」は、その API・UI・関数が実在するかを grep で見る。本文の数値（件数・ジョブ数・行数）、「概算」と断った値、「実測が無い」という主張は数え直す（`gh run list` などで 1 回で覆るものは必ず叩く）。正しければそのまま従う
- 前提が崩れていたら決定に従わず、PM に諮る（開発リーダーは利用者へ直接聞かない）。決定が確定済みの Issue の本文は自動の Issue レビューで書き換えない。逸脱は設計方針書に理由と根拠の file:line を書く
- 契約を書く前に、直す対象の型・フィールドについて、定義・すべての生産者・すべての消費者・既存のテスト・似たフィールドを洗い、結果を goal に事実として書く。自分で調べて書いた Issue でも、最初に見つけた 1 か所を原因と決めて別の生産者を取りこぼしていることがある（片方だけ直すとテストは緑のまま穴が残る）。この洗い出しは `scope.allow` を決めるのにも使う
- 行の由来（どのコミットで入ったか）を書くときは `git blame -L <行範囲> <ref> -- <file>` を使い、出力（コミットと日付）をそのまま貼る。`git log -1 -- <file>` はファイルに最後に触ったコミットで、その行を入れたコミットではない
- 「0 件」「前例なし」を根拠に書く前に陽性対照を撃つ（同じファイルで在ると分かっている語が同じコマンド形で当たることを見る）。リテラルは `grep -F` で探し、ERE（`grep -E`）に `\|` を書かない。識別子は定数・enum 越しに参照されることがあるので、リテラルで 0 件なら定義側のシンボル名でも引く。契約に「前例は N 件」と書くなら、そのコマンドと出力を貼る
- goal には「本文と実コードが食い違えば実コードを正とし、訂正をコミットメッセージに書く」を入れる。ワーカーの逸脱の報告は、契約の誤りを直す材料として受ける

- Phase 1 では本文と一緒にコメントも取る（`gh issue view <N> --comments`、または `--json body,comments`）。起票の後に Q&A のコメントで方針が確定していることがあり、本文と逆のこともある。コメントに確定した方針があれば、契約の goal の「方針」はそれを正として書き、本文と食い違う点を明記する。「別 Issue で」と答えられた項目は scope から外す

## 2-4 Issue と契約にコードを載せるとき

- `gh issue view --json body` と `gh api` は、本文のコードの `\u00XX`（C0 制御文字）を `\^A` のようなキャレット表記に変えて返す。ワーカーは gh で本文を読むので、写したテストが黙って別の文字列になる。制御文字は `String.fromCharCode(0x1b)` や `\x1b` で書く
- パッチ全体を code fence で載せるとき、パッチの中に ```` ``` ```` があると外側の fence がそこで閉じる。外側は 4 連のバッククォートにする
- 本文をファイルに書いて `--body-file` で渡すとき、書いた道具が `…` のようなエスケープを実の文字に変えることがある。登録の前に `grep -c 'u2026' <file>` のように残っているかを確かめる
- 確定仕様を全文で載せた Issue は、起票の後に `gh issue view <N> --json body --jq .body` で取り直し、コードブロックを検証済みのファイルとバイトで比べる

## 2-4 契約の配り方と scope.allow の書き方

- **文の禁止と scope.allow を食い違わせない**: 契約の文（decisions・制限）で禁じても、`scope.allow` に入っていればワーカーは書き、verify も赤にしない（機械の許可が勝つ）。`contract.mjs generate` は `changelog.d/<issue>.md` を必ず allow に足し、goal に断片の書き方を入れるので、断片を書かせない回は生成した yaml から allow の行と goal の断片の節を消し、`grep -n changelog <yaml>` で残りが無いことを確かめてから送る。逆に文や再指示で範囲を広げるときは、名指ししたパスが allow に入っているかを送る前に確かめ、入っていなければ契約を作り直す（複数回の契約では最後の契約の allow で scope が裁定される）
- scope の glob では `[` と `]` は文字そのもの。Next.js の動的ルートは `src/app/api/worktrees/[id]/auto-yes/route.ts` とそのまま書く（シェルのエスケープの `[[]id]` は一致せず scope で exit 20 になる）。`*` で書いてもよい
- **契約は未コミットで配ってよい**。`work-evidence` / `scope` ゲートは変更集合から契約ファイル自身を
  除外する（#1580）ので、契約を置いただけの worktree が「作業済み」に見えることはない。
- `scope.allow` は**Issueが触ると宣言した範囲**を書く。広すぎる allow は scope ゲートを無力化し、
  狭すぎる allow は正当な変更を不合格にする。迷ったら Phase 1 の依存関係分析で洗い出した
  ファイル集合をそのまま使う。

## 2-4 scope.allow に対のテストを入れる探し方

- `src/` のファイルを `scope.allow` に入れたら、そのファイルを検査しているテストも入れる（ワーカーは scope 外のテストを直さず報告するだけなので、漏れると検証が落ちる）。探すのは名前の推測ではなく grep: 変える関数・定数名で `grep -rl "<名前>" tests/`、モジュールを差し替えているテストを `grep -rl "vi.mock('@/<モジュールのパス>'" tests/`（export を足すと部分モックに無くて落ちる）、値や挙動を変えるなら変える前の値そのもの（`grep -rn "'<旧い値>'" tests/`。定数名を使わずリテラルで固定しているテストがある）
- `tests/unit/` には `lib/` の有無で同じモジュールのツリーが 2 つある（`tests/unit/hooks` と `tests/unit/lib/hooks`、`detection`・`polling`・`cli-tools` も）。`find tests -path '*<module>*'` で全部拾い、書いた glob が 0 件でないことも確かめる
- 定数の正本（`src/config/*.ts` など）を入れたら `tests/unit/config/<同名>.test.ts` を無条件で入れる（配列の identity を固定していることがあり、値を保った差し替えでも落ちる）
- 受入条件が「表示される・答えられる」のように層をまたぐときは、`grep -rl "<検出層の関数名>" src/` で既存の消費者を全部見て、同じ判断を通すべきものを入れる
- 列挙値（CLI tool id・hook の種類・権限モードなど）を足す Issue は、同種の既存の値で `grep -rln '<既存の値>' src tests docs .claude scripts` を回し、ヒットしたファイルをそのまま allow に入れる（`Record<…>` の型・一覧を固定するテスト・docs のツール一覧が一斉に赤になる）
- `docs/<path>.md` を入れたら `docs/en/<path>.md` も入れる（`tests/unit/docs/ja-en-heading-parity.test.ts` が見出しの対応を強制する）
- 範囲の漏れで落ちたら、まず自分の allow を疑い、違反ファイルごとにそれを強制したテスト・ガードを実測で特定する。再指示の回数に数えず、scope を広げた契約を `--contract` で送り直す（scope は送信時のスナップショットで、yaml を直すだけでは変わらない）

## 2-4 変異注入の戻しの確かめ方

契約に変異注入（一時的にコードを壊して、テストが落ちることを示す）を書くとき、戻したことの確認を `git diff --exit-code -- <file>` が exit 0、と書いてよいのは、そのファイルが `scope.allow` に入っていない（この Issue で変えない）ときだけ。`scope.allow` に入っているファイルなら「変異の前に `cp` で複製を取り、戻した後に複製と `diff -u` が無差分」と書く。そうしないと、正しく実装したワーカーほど条件を満たせない。別の Issue の契約から文面を写すときも、この点を見直す。

## 2-4 実装方針を書くときの確かめ

- 契約や起票で既存のヘルパを使えと指示するときは、そのヘルパが何を対象にするかを先に自分で読む（例: システムディレクトリの判定が `/tmp`・`/var` まで含み、`os.tmpdir()` を使うテストの隔離を壊す）
- 失敗時の方向（allow か ask か、fail-open か fail-closed か）はツールごとに逆のことがある。推測で決めず、確かめた結果か「推奨」として書く
- 同じ穴を横展開する Issue は、並行する開発がすべて着地してから範囲を取り直す（着地前の調査は古い。並行の開発自身が同じ形の穴を増やすことがある）
- ワーカーがコミットに書いた「本文からの意図的な逸脱」は、マージの前にオーケストレーターが grep などで独立に裏を取る

## 2-4 広い移行の Issue の網羅を数で確かめる

広い機械的な移行（生の UI 要素 → 共通部品など）の Issue は、ワーカーが強調された手順だけをこなして本体を残したまま完了にすることがある。ゲートが緑でも網羅は別。受入基準に残数の数え方（例 `grep -rE '<button' src/components/<dir> --include='*.tsx' | wc -l` をディレクトリ別に）と目標値を書き、完了後にオーケストレーターが同じコマンドで数える。変更したファイルの数が想定より極端に少なければ未達を疑う。
未達が大きく危険な画面に及ぶなら、独断で全面移行を強制せず、残りを別 Issue に分けるかを利用者に訊く。
新しい操作の UI（パレット・ダイアログ・フォーカストラップ）は、テストがイベントをフォーカスの当たらない要素へ直接撃っていないかを見る。実際のフォーカス経路（`document.activeElement`）を通すテストを受入基準に入れる。

## 2-4 実際に起きた失敗を直す契約

実際に起きた失敗を直す Issue は、run の記録・ログに残った出力をそのまま fixture にすることを受入基準に書く（ワーカーが文面を作ると、陽性対照がすべて緑でも本物の形に当たらないまま検証とレビューを通る）。マージの前に、オーケストレーターが実測のログと判定（正規表現など）を自分で突き合わせる。

## 2-4-2 テスト全体の書き方の方針

書き方は次の方針にしている:

- **禁止は「テスト全体」に限る**。対のテスト・lint・tsc は数十秒で終わるので、ワーカーが自分で確かめられる
- **待ち方は肯定形で書く**。特定の機能名を出して禁じると、かえってその機能を意識させるおそれがあるため
- **守られる保証は無い**。3-3 の合図確認は、この指示の有無にかかわらず行う

## 2-4-2 sonnet 担当とサブエージェント

サブエージェントについての指示は要らない: `.claude/agents/*.md` は `model: inherit` なので、ワーカーがサブエージェントを呼んでも
    セッションと同じモデル（sonnet）で走る（`model: opus` 固定だった頃は、その部分だけ opus で走っていた）
