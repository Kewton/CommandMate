# 実機確認手順書: 端末間の通知消し込み（Issue #2001）

- **対象**: `feat(push): 待機が解決したら他端末の通知を無音で置き換える (#2001)`
- **設計の根拠**: [docs/design/cross-device-notification-dismissal.md](../design/cross-device-notification-dismissal.md)
- **なぜ実機が要るか**: 自動テストはサーバのファンアウトと Service Worker のハンドラを
  固定できるが、**通知シェードの実挙動・音・バイブ・iOS の購読寿命**は実機でしか取れない。
- **所要**: 準備 15 分 + 実施 30 分程度

> 先に読むこと: 本 Issue は「無音で送って表示せず close だけ」という当初案を**棄却**している。
> したがって **解決時に「対応済みです」というカードが 1 枚見えるのが正常**である。
> カードが 1 枚も出ないのは仕様ではなく異常（§5 の記録対象）。

---

## 1. 準備

### 1.1 必要なもの

- iPhone 1 台（iOS 16.4 以上。**ホーム画面に追加した PWA から開くこと** — iOS は
  インストール済み PWA 以外では Web Push を許可しない）
- Android 1 台（Chrome）
- CommandMate サーバ（HTTPS で両端末から到達できること。VAPID 鍵が設定済みであること）
- 待機を作れる worktree 1 つ（例: `claude` で承認プロンプトが出る作業を投げる）

### 1.2 前提の確認

```bash
# サーバに VAPID が設定されているか（未設定だと push が 1 通も出ない）
curl -s https://<host>/api/push/vapid | head -c 200
```

両端末で **設定 → 通知** を開き、次を確認する。

- [ ] 「この端末で通知が有効です。」と表示される（両端末）
- [ ] 「対応が必要なとき」が **ON**（両端末）— 消し込みはこのバケツに属する
- [ ] Service Worker が更新されている。**アプリ内の「更新があります」トーストを必ず適用する**
      （本 Issue は `public/sw.js` を変更している。旧 SW のままだと `resolved` を解釈できず、
      解決通知が「対応済み」の**通常カード**として鳴る＝誤った結果になる）

Service Worker の版を確かめる確実な方法（Android Chrome）:

1. `chrome://inspect/#service-workers` を PC から開く（USB デバッグ）か、
   端末で `chrome://serviceworker-internals` を開く
2. 該当スコープの SW を選び、`replaceStaleNotifications` が含まれているか確認する

iOS には同等の画面がないため、**一度アンインストール（ホーム画面から削除）→ 再追加 →
通知を再許可** して確実に新しい SW を取り込むのが速い。

### 1.3 サーバログを流しておく

判定は理由コードつきでログに出る。実施中は次を流しておくと、
「鳴らなかった」と「壊れている」を切り分けられる。

```bash
# resolution-push-sent / resolution-push-skipped の reason を見る
tail -f <server log> | grep -E 'push/resolution|push/waiting-notifier|push/prompt-gate'
```

期待される行の例:

```
[INFO] [push/resolution] resolution-push-sent {"worktreeId":"...","instanceId":"claude","reason":"cross-device-clear","deviceCount":2}
[INFO] [push/resolution] resolution-push-skipped {"worktreeId":"...","reason":"single-device","deviceCount":1}
[DEBUG] [push/resolution] resolution-push-skipped {"worktreeId":"...","reason":"no-card"}
```

## 2. 本体: 双方向の消し込み

### T-1. iPhone で応答 → Android のカードが置き換わる

1. 両端末をロックし、画面を消す（バックグラウンド配送を確かめるため）
2. PC から worktree に、承認プロンプトが出る作業を送る
3. **両端末**に「`<worktree名>` (claude) / 応答待ち: …」が届くことを確認する
4. **iPhone で通知をタップ**し、開いたアプリからプロンプトに応答する
5. **Android の通知シェードを開く**

**期待**:

- [ ] Android のカードが「応答待ち: …」から **「対応済みです（他の端末で応答されました）」**
      に変わっている（**カードが増えて 2 枚になっていない**こと）
- [ ] その置き換えのときに Android が **鳴らない・振動しない・画面が点灯しない**
- [ ] iPhone 側には「対応済みです」のカードが 1 枚出る（タップで消したため置き換え先が無い）。
      これは §6 の「残る不正確さ」として設計上想定内であり、**無音であれば合格**
- [ ] サーバログに `resolution-push-sent` / `reason: cross-device-clear` / `deviceCount: 2`

### T-2. Android で応答 → iPhone のカードが置き換わる（逆方向）

T-1 の 4 を「**Android でタップして応答**」に替えて繰り返す。

**期待**:

- [ ] iPhone のカードが「対応済みです（他の端末で応答されました）」に置き換わっている
- [ ] 置き換えのときに iPhone が鳴らない・振動しない
- [ ] **iPhone の通知が 2 枚に増えていない**（増えていたら iOS の `tag` 置換が効いていない ⇒ §6 に記録）

### T-3. 通知をタップせずに応答した場合（本命のケース）

現実にはこれが最も多い。**どちらの通知にも触らず**、PC のブラウザまたはターミナルで応答する。

**期待**:

- [ ] **両端末**のカードが「対応済みです」に置き換わる（どちらも 0 → 1 ではなく 1 → 1）
- [ ] どちらも鳴らない・振動しない

### T-4. Auto-Yes が答えた待機では何も起きない（#1999 の維持）

1. `commandmate auto-yes <worktree-id> --enable` で Auto-Yes を有効にする
2. 承認プロンプトが出る作業を送る

**期待**:

- [ ] 待機通知が **来ない**（#1999 の挙動）
- [ ] Auto-Yes が答えたあとも **「対応済み」通知が来ない**（消すカードが無いため）
- [ ] サーバログに `resolution-push-skipped` / `reason: no-card`

> ここで「対応済み」が鳴ったら、それは #1999 の削減を食い潰している状態＝不合格。

## 3. 端末台数の境界

### T-5. 購読が 1 台のとき、挙動が変わらない

1. **Android の通知を解除**する（設定 → 通知 →「この端末の通知を解除」）
2. iPhone 1 台だけの状態で T-1 の 1〜4 を実施する

**期待**:

- [ ] iPhone に待機通知が届く（従来どおり）
- [ ] 応答後に **「対応済み」通知が来ない**（1 通も増えない）
- [ ] サーバログに `resolution-push-skipped` / `reason: single-device` / `deviceCount: 1`

### T-6. 購読が 0 台のとき、例外が出ない

1. **両端末の通知を解除**する
2. 承認プロンプトが出る作業を送り、応答する

**期待**:

- [ ] サーバが落ちない・ポーリングが止まらない（worktree の状態表示が更新され続ける）
- [ ] ログに `push-fanout-error` / `resolution-push-failed` / 未捕捉例外が **出ない**
- [ ] `reason: no-card` の debug 行だけが出る（購読 0 件ではカードのマークも付かないため）

### T-7. 片方が「対応が必要なとき」を OFF にしたとき

1. 両端末を再購読し、**Android だけ**「対応が必要なとき」を OFF にする
2. 承認プロンプトが出る作業を送り、応答する

**期待**:

- [ ] iPhone にだけ待機通知が届く
- [ ] 応答後に「対応済み」通知が **来ない**（要対応バケツの購読が実質 1 台のため）
- [ ] `reason: single-device` / `deviceCount: 1`

## 4. 「音・バイブを伴わないこと」の確かめ方

体感に頼らず、次のどれかで機械的に確かめる。

**Android**:

1. 端末を**マナーモードではなく通常モード**にし、音量を上げておく（鳴るなら鳴る状態にする）
2. 通知シェードを開いたまま置き、T-3 を実施する
3. カードの文面がその場で書き換わるのを見る。**このとき音が鳴らない／端末が震えない**こと
4. あわせて `設定 → 通知 → 通知履歴`（Android 11+）を開き、
   解決通知が「音を鳴らした通知」として記録されていないことを確認する

**iPhone**:

1. サイレントスイッチを **オフ（＝鳴る側）** にする
2. T-3 を実施し、バナーが**出ずに**通知センター内のカードだけが更新されることを確認する
   （音が鳴った場合は §6 に記録。iOS の `silent` は端末設定にも従うため、
   ここが唯一「実機でしか分からない」箇所である）

## 5. 「新しい通知が表示されないこと」の確かめ方

本設計では **カードは 1 枚出る**（それが契約）。したがって確認すべきは
「**枚数が増えないこと**」であって「1 枚も出ないこと」ではない。

1. T-3（どちらの通知にも触らない）を実施する
2. 各端末の通知シェードで **CommandMate のカードの枚数を数える**

**期待**: 応答前 1 枚 → 応答後も 1 枚。

**枚数が 2 枚になった場合**は `tag` による置き換えが効いていない。設計の想定外なので §6 に記録する
（`tag` は両方とも `<worktreeId>:prompt` のはずで、`getNotifications`→`close` も走っている）。

**「このサイトはバックグラウンドで更新されました」/「This site has been updated in the
background」が出た場合**は、`userVisibleOnly` 契約の違反を Chrome が検知している。
本設計では発生しないはずなので、**発生したら即座に §6 に記録して報告すること**
（`showNotification` が呼ばれていない＝ SW が古いか、close が show の後に走っている）。

## 6. 記録テンプレート（次の Issue の材料になる形）

不成立を見つけたら、次の形で記録する。**「動かなかった」だけでは次の Issue が書けない。**

```markdown
### 事象
- 端末: iPhone 15 / iOS 18.5 / ホーム画面 PWA / Safari
- テストケース: T-2
- 期待: 既存カードが「対応済みです」に置き換わる
- 実際: 既存カードが残ったまま、「対応済みです」が 2 枚目として増えた

### 取った証跡
- 通知シェードのスクリーンショット（応答前 / 応答後）
- サーバログの該当行（reason と deviceCount を含む行をそのまま）
- 端末側で `getNotifications` が何を返したか（後述の採り方）

### 切り分け
- [ ] Service Worker は新しいか（§1.2 の手順で確認した）
- [ ] 同じ操作を Android でやると期待どおりか（＝ iOS 固有か、両方か）
- [ ] 購読が生きているか（この操作の**あと**に新しい待機通知が届くか。
      届かなくなっていたら purchase 取消＝ userVisibleOnly 違反を疑う）
```

### iOS で `getNotifications` の戻りを採る

iPhone を Mac に繋ぎ、Safari の **開発 → \<iPhone名\> → Service Worker** から
コンソールを開いて次を実行する。

```js
// いま自分が表示していると思っている通知
(await self.registration.getNotifications()).map(n => ({ tag: n.tag, title: n.title, body: n.body }))
```

- **空配列が返るのに通知センターにはカードがある**なら、iOS の `getNotifications` は
  配信済み通知を返していない。これは本 Issue の「補強」（§6 of 設計書）が効かないという意味で、
  **設計の主経路（同一 `tag` での置き換え）が効いているかどうかを別に判定する**必要がある。
  そのときは T-3 の枚数（1 → 1 か 1 → 2 か）が判定材料になる。
- この結果は次の Issue の中心になるので、**必ずそのまま貼ること**。

### 購読が取り消されていないかの確認

本設計は silent push を 1 回も出さないので、購読が取り消されることは無いはずである。
念のため、一連のテストの**後**に:

1. 新しい待機を作り、両端末に待機通知が届くことを確認する
2. 届かない端末があれば、設定 → 通知 で「この端末で通知が有効です」がまだ出ているかを見る
3. 消えていれば購読が取り消されている ⇒ **重大**。§6 の形で記録し、
   `resolution-push-sent` が何回出たあとに起きたかを添える

## 7. 合否のまとめ

| # | 確認項目 | 合格条件 |
|---|---|---|
| T-1 | iPhone で応答 → Android | カードが「対応済み」に**置き換わる**（増えない）、無音 |
| T-2 | Android で応答 → iPhone | 同上（逆方向） |
| T-3 | 通知に触れず応答 | **両端末**とも 1 枚 → 1 枚で置き換わる、無音 |
| T-4 | Auto-Yes 下 | 待機通知も解決通知も**来ない**（`reason: no-card`） |
| T-5 | 購読 1 台 | 解決通知が **1 通も増えない**（`reason: single-device`） |
| T-6 | 購読 0 台 | 例外なし・ポーリング継続 |
| T-7 | 片方が要対応 OFF | 解決通知が来ない（`deviceCount: 1`） |
| §4 | 音・バイブ | どの解決通知でも鳴らない・震えない |
| §5 | 枚数 | 増えない。Chrome の汎用カードが**出ない** |
