- **feat(orchestrate): `merge-pr.mjs --queue` でマージを 1 本ずつ流し、machine-lock を先着順の札にして、マージがロックの取り合いで止まらないようにする** (#4277): `merge-pr.mjs --queue <issue[/item][@pr],...>` が entry を 1 つのプロセスで順にマージする（PR → branch → worktree を**変更の前に全部**解決し、曖昧なら何も変えずに exit 2。exit 3 は 60 秒おいて 2 回、exit 4 はすぐ 5 回まで自動でやり直し、それ以外は列を止める。状態は run の記録の `queue` の行で、HEAD を持たず進捗に数えない＝`readRecords` の `logRecords`、`status` の `queue`）。1 本の呼び出しも列も base ごとのマージのロック `merge.<owner>.<repo>.<base>` を持ち、merge-pr は自分を専用のプロセスグループとして起動し直す（親の環境はそのまま継ぐ）ので、親だけが死んでも残った `git push`・`gh pr merge` と次のマージが重ならない。push / merge / close の途中で死んだ持ち主は `.unresolved/` に記録され、その PR を流すまで後の merge-pr はどれも何も変えずに止まる。machine-lock（`machine-lock.ts` と同期の写し `scripts/orchestrate/machine-lock-sync.mjs`。gate-runner・precheck・merge-pr）は待つ側が先に札（`<name>.queue/<12 桁>`、`link(2)` で公開・番号は再利用しない）を取り、**生きている札の先頭だけが `mkdir` を試す**ので、5400 秒待つ precheck が後から来た検証に抜かれ続けることが無くなる（2026-11-08 の run では #4262 の 109 分のうち 67 分がこの取り合い）。死んだ札（ESRCH・pid の再利用・期限＋猶予）は外れ、死んだ保有者のロックは列の先頭だけが退かしてから回収し、解放は 1 回きりで他者のロックを動かさない。standalone の `verify-run.sh`（`.claude` と `.agents`）も同じ札・先頭だけの回収・`pgid` に従うので、TS の回収が死んだ保有者のロックを退かしている間に bash の素の `mkdir` が入り込んで 2 者が同時に持つことも無くなる（`commandmate-skills` の写しへの移植は別途）。マージのロックと `.unresolved/` は lock root の下の専用の `merge/` に置くので、verify.yaml の `mutex` に同じ名前を書いたゲートの回収が停止の記録を迂回することは無く、未確認の書込みを列の先頭へ出したときは Issue を閉じる entry を実行の順で決め直す（同じ Issue の全 entry がマージされるまで閉じない）。
