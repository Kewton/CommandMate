[38;5;231m[49m⏺[39m [1mHow Terminal Multiplexers Survive Disconnects[0m

  When you SSH into a machine and run a long job, the job dies the moment your connection drops. Terminal multiplexers like tmux and GNU Screen exist to break that coupling, and understanding how
  requires knowing what actually kills the process.

  [1mThe problem: SIGHUP and the controlling terminal[0m

  Every interactive process is attached to a [3mcontrolling terminal[0m — historically a physical teletype, today a pseudo-terminal (PTY) pair. A PTY has two ends: the master, held by whatever is drawing
  your screen (sshd, your terminal emulator), and the slave, which the shell and its children open as stdin/stdout/stderr.

  The kernel tracks which session each process belongs to and which terminal that session controls. When the master end of the PTY closes — your SSH connection drops, you close the window — the kernel
  notices the terminal has been hung up. It delivers [38;5;153mSIGHUP[39m to the foreground process group, and the session leader propagates it to its children. The default disposition of SIGHUP is termination.
  Your job dies not because the network failed, but because the kernel deliberately told it to.

  [1mThe solution: put a server in between[0m

  A multiplexer splits the arrangement into two processes. When you first run [38;5;153mtmux[39m, it forks a long-lived [1mserver[0m daemon that detaches from your terminal entirely — it calls [38;5;153msetsid()[39m to become its own
  session leader with no controlling terminal, so there is no terminal that can ever hang up on it.

  That server then allocates its [3mown[0m PTYs, one per window or pane, and spawns your shells against those. Your shell's controlling terminal is a PTY owned by the server, living entirely inside the
  machine. It has no relationship to your SSH connection.

  What you interact with is a thin [1mclient[0m process. It connects to the server over a Unix domain socket (typically under [38;5;153m/tmp/tmux-$UID/[39m), forwards your keystrokes in, and renders the screen updates
  the server sends back. When your connection drops, only the client dies. The server never notices anything beyond a closed socket; it keeps reading output from the still-running shells and updating
  its in-memory screen model.

  [1mReattaching[0m

  Running [38;5;153mtmux attach[39m starts a new client, which connects to the same socket. The server replays its saved screen state — cursor position, scrollback, pane layout — and you're back exactly where you
  left off.

  This is also why [38;5;153mnohup[39m and [38;5;153mdisown[39m are weaker alternatives: they suppress SIGHUP but discard the terminal, so you lose interactivity and output. A multiplexer preserves both.
