- **fix(polling): worktree ID の一括移行で保留中の画面読み取りが置き去りになり、退役した tick がそれを書き換える問題を修正** (#3663): `migrateResponsePollerWorktreeIds` は poller と dedup の状態を新しい ID へ移していたが、#2436 の保留（`__pendingScrapedResponses`）は旧キーに残り、確定されても旧 ID のままなので外部キーで失敗して返答が消えていた。保留は全移送元を先に退避してから移送先へ置き（入れ替え・連鎖・paused も）、本文・期限・timestamp・付帯情報を保って worktreeId だけ新しい ID にする。移送先で既に動いていた鎖は止め、その保留は今の ID で先に確定する。解決できずに止める鎖の保留は新しい ID で確定する。あわせて保留の倉庫は、呼び手の tick が退役（`stopped`：停止・60 秒超の再起動・移行）していれば自分のキーへの作成・本文更新・削除・確定を拒否し（別セッションへの操作、たとえば relay 配達からの再起動の確定は通す）、期限の settle は await の後に呼び手と「同じキーの同じエントリー」を確かめてから discard / flush する。通常の待機つき再起動（`superseded` だけ）の tick は従来どおり hold でき、再起動時の停止で確定される。保留だけ（鎖も pause も無い）を移すときも移送先の鎖を止めて既存の保留を確定する。移行の時点で tick が走っている鎖（`running` の記録の owner がそのキーの今の owner と同じもの）は、移送元のキーの上でだけ応答のハッシュを捨ててから一括で移す（多対一の移行で別の移送元から届いたハッシュは残る）（その tick はハッシュを登録した後で保存か保留かがまだ決まっておらず、移すと後継が未保存の返答を重複と見て取りこぼす）。後継は同じ画面を自分で判定して保留・保存する。代わりに、移行の瞬間にその tick が保存を終えていた返答は、後継がもう 1 行保存しうる（欠落より重複を取る、#2436 と同じ判断）。tick が走っていなかった鎖・paused の鎖は従来どおりハッシュを移し、画面の返答を二重保存しない。停止した鎖の tick は自分のキーへ応答のハッシュを登録しない（保留の倉庫と同じ判定）。prompt のハッシュと prompt-skip の扱いは変わらない。
