- **fix(relay): 返事の配送が依頼元の解決に失敗すると推定の claude へ打ちうる問題を修正** (#4498): relay の配送（`relay-delivery.ts` の `attemptDelivery`）は依頼元を `resolveRelaySession` で解決しており、名簿の読みが一度失敗すると表示用のフォールバック（claude）が返り、その推定の tool で規則 0（#4437）の判定も `sendUserMessage` の送信先も決めていた。同じ instance id の claude のペインが残っていれば、codex へ返すべき返事が claude に打たれうる。配送は新しい `tryResolveRelaySession`（失敗で null。`resolveRelaySession` の表示用の振る舞いは不変）で依頼元を **1 回だけ** 解決し、その結果で準備確認（readiness）・規則 0・送信先をまとめて決める（方針の側で読み直さない）。準備確認の待ちの後の解決に失敗したとき、共有の resolver が最後の推定（worktree が使える tool を宣言していないときの claude）しか返さないとき、名簿に登録されていた instance の行が消えて同じ ID が別の tool（worktree の既定）に解決されるときは、claim の前に **保留**（`held`、ログ `relay-delivery-held reason=resolve-failed` / `roster-row-gone`）にして payload を残し、次の pump で正しい送信先が分かれば 1 回だけ打つ（名簿に一度も無い ad-hoc の ID は従来どおり worktree の既定へ送る。行の消失の記憶はメモリにあり、サーバーの再起動で忘れる）。期限切れ・取り消しの経路はそのまま効く。なお、Antigravity の利用を申告していない既定の設定では、名簿の読みが待ちの前から失敗している端は規則 0 が全 tool として判定するため、保留ではなく relay が取り下げられる（#4496 からの挙動のまま）。あわせて、既定 codex の worktree へ ad-hoc の `--agent claude --reply-to` で送った bound relay は、送信直後の判定が `to` を既定の codex として観測し直して `generation_changed` の保留に入り、返事が戻らなかったため、境界を記録したときの tool（実際に打った claude）で観測するようにした。また、規則 0 で断られた bound `/send` は取り下げの成否を応答の `relayWithdrawn` に載せ、取り下げの DB 書込みが失敗したときは `was withdrawn` と断言せず「取り下げを確かめられない（まだ開いているかもしれない）」旨の文にした。CLI（exit 33 の 4 行目）も、作成時の拒否（`The relay was not opened`）・作成後の取り下げ・取り下げを確かめられない場合（`commandmate relays cancel <id>` を案内）の 3 つを区別して表示する。
